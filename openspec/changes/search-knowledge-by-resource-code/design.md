## Context

当前 knowledge_search 强制 knowledge_base_id。资源页面显示 retrieval_resource.code，而目录返回 knowledge_base.code，二者可能不同。资源编码已有唯一约束，检索已统一执行 Job、应用、角色、发布及来源授权。

## Goals / Non-Goals

**Goals:** 用户提供资源编码即可查询；服务端精确定位，检索结果继续携带规范知识库 ID，供后续代码核验使用。

**Non-Goals:** 不增加别名表、模糊编码匹配、跨库检索或自动授权；不改变现有索引数据和 ONES 在线权限策略。

## Decisions

- 新增 resource_code，与 knowledge_base_id 严格二选一。避免把编码塞入 ID 参数而产生歧义。
- 身份核验后，通过唯一资源编码定位资源，先检查知识库授权，再检查启用及发布状态。未知和无权编码统一拒绝；已授权失效资源沿用现有不可用错误。
- 固定解析出的资源身份，后续仍使用现有资源解析、配置和授权复核；不得因同库另一资源启用而把旧编码自动指向新资源。
- 目录 code 改为资源编码，Agent 提示优先使用用户明确编码；未提供编码时才查目录。代码检索仍要求环境和 SVN 版本，后续源码工具使用检索返回的 ID。
- 共享合同和 Prompt 版本、测试同步更新；部署 API、Worker、MCP 和两个 Runtime，发布 assist03 使用的新合同，不覆盖历史发布。

## Risks / Trade-offs

- 工具合同变化使旧发布失配 → 部署前核对受影响应用，仅更新本次授权范围内的绑定，明确其他发布需要更新。
- 编码存在性泄露 → 未知与未授权返回同一安全错误，无正文查询或索引调用。
- 编码与资源替换竞争 → 校验检索固定资源的 ID，保留现有发布配置变化拒绝机制。

## Migration Plan

无需表迁移。先验证合同、授权和检索测试，再更新服务与新发布；回退时须同时回退服务和应用绑定。
