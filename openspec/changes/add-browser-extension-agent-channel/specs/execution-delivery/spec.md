## ADDED Requirements

### Requirement: 插件在模型生成期间收到有界的用户可见回答文本

受信原插件会话路线 SHALL 在 Runtime 工具合同校验通过后，把主对话助手的 Markdown 正文按生成顺序分批编码为现有 `assistant_text` 事件，包括工具前后的普通说明。Worker MUST 校验 claim、invocation、digest 与源 sequence。每个可用增量必须可在本次执行结束前供原用户订阅。思考、系统消息、工具参数或原始结果、子任务、原始 SDK 及审计块 MUST NOT 进入对外数据流。成功消息保留本次 attempt 的全部助手正文。完整消息和 ResultMessage 不得与增量重复追加。

#### Scenario: 使用真实流式模型生成长回答
- **WHEN** 模型仍在生成后续公开文本，用户已经订阅 Job
- **THEN** 插件已展示第一段，随后能看到至少一个新片段，Job 成功提交后显示与权威助手消息一致的最终文本

#### Scenario: 工具调用与回答交错
- **WHEN** SDK 产生普通工具前叙述、思考、工具输入、工具结果及其后的用户回答
- **THEN** 用户在调用工具前即可读到助手说明，随后在同一回复中读到结论。重开会话后两段正文各出现一次，顺序一致，工具输入输出与思考块均不进入正文

#### Scenario: 上游仅返回整段或达到流协议预算
- **WHEN** 当前调用无法可靠获得公开增量，或继续产生预览会挤占既有协议的终态或审计预算
- **THEN** 服务保留安全状态和可提交的最终结果；不得通过切分终态冒充实时生成，验收记录区分实际流式与降级

### Requirement: 原插件会话可以从断点恢复且只呈现一个最终结果

系统 SHALL 提供用户级 SSE 和会话结果读取。同一 Job 的对外事件游标 MUST 严格递增；同一 invocation 的已接受源序号幂等，旧 Worker 失去 claim 后不得追加。短期回答内容必须与普通事件审计隔离，按 Job 授权和有界期限清理。终态以 Job 与有序助手消息的持久事务为准，客户端不得将临时预览保存为第二条助手消息。

#### Scenario: 断线、重复事件及重新打开
- **WHEN** 网络中断、插件关闭或授权到期后，用户在当前有效权限下重新接入
- **THEN** 带已渲染游标时只应用后续事件；丢失草稿时从可用预览或权威快照恢复；不会重跑 Job 或重复追加文字，短期记录清理后仍可按正常生命周期读取终态

#### Scenario: 已展示部分回答时凭据到期
- **WHEN** 原 SSE 订阅的凭据到期，原用户静默换证或重新登录后仍有该 Job 的读取权
- **THEN** 服务端 MUST 停止旧流且保留 Job 的正常执行。插件携新凭据和最后已渲染的 Last-Event-ID 订阅同一 Job，忽略迟到或重复事件；草稿或游标不可用时取快照，在等待登录期间已完成则取已提交结果，不重启执行

#### Scenario: 快照与重连之间产生重试或终态
- **WHEN** 本地只剩游标却没有对应草稿，或打开事件流时收到 cursor_invalid，且读取快照后出现 reset 或终态
- **THEN** 客户端 MUST 使用 GET /jobs/{id} 返回的同一版本草稿及 through_cursor 整体恢复，再订阅该游标之后的全部事件。终态直接呈现。没有终态的 EOF 不能标记成功；原 Job 继续运行

#### Scenario: 已显示部分文本后重试、失败或取消
- **WHEN** 同一 Job 开始新的 attempt，或最终失败、超时或取消
- **THEN** 新 attempt 先明确重置旧预览；最终失败用安全终态替换未完成预览，迟到的旧 attempt 不能覆盖它

#### Scenario: Runtime 已完成但 Worker 本地提交失败
- **WHEN** Runtime 终态可重放而 Job 和助手消息事务尚未提交
- **THEN** 客户端不能收到成功终态；Worker 恢复后只交付同一已提交结果，不触发外部投递或第二次业务执行

### Requirement: 录制的多轮诊断按 Job 引用取证

有录制绑定的 Job MUST 沿用既有运行输入，在本轮问题和有界会话上下文之外仅增加版本的安全引用与覆盖概况。Worker 和 Runtime MUST 沿用每个 Job 独立沙箱及终态清理；不得将录制索引或明细作为附件自动下载、挂载或整段拼接到提示词。经授权的受控工具仅把本轮所需的有界命中或明细返回模型。Job 重试 MUST 复用原绑定并重新检查读取权限。

#### Scenario: 同一录制连续排查后改写上一轮结论
- **WHEN** 首轮 Job 已清理沙箱，第二轮追问同一请求的业务码，第三轮仅要求缩短已有回答
- **THEN** 第二轮可按带来源的证据 ID 取明细，无需重新上传、建索引或恢复旧沙箱；第三轮可用有界历史直接回答。三轮均不自动向 Runtime 传输整份录制
