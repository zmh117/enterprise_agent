## Context

主平台和知识当前为同机两套 Compose project。API 按主文件重建后遗漏知识 bootstrap，内部兑换被拒绝；知识容器仍 healthy。canonical `platform-operations` 原要求独立知识 Compose，本 change 明确改为单一主入口。

## Goals / Non-Goals

目标：主 Compose 默认启动七个知识常驻服务，自动等待模型准备、schema 和必要依赖；网页/CLI 可以独立管理六个知识业务服务。复用现有四个卷，保持认证、授权和采集计划不变。

不新增远程部署管理、任意 Compose 文件选择或配置生成层，不改变模型与检索算法，不提交或推送其他工作。

## Decisions

1. 所有服务定义直接位于根文件，删除过时叠加/独立文件，避免两套部署定义漂移。模型准备作为一次性启动依赖；手工检查、导入命令保留 maintenance profile。
2. API 与 Knowledge MCP 共享既有知识 bootstrap 文件；只给 API/MCP 相应角色身份。平台数据库仍为唯一迁移责任方，知识 worker 使用同一平台连接。
3. 保留独立执行器，固定主项目及根文件；只接受固定服务白名单，所有知识 `up` 均 `--no-deps`，因此不会经依赖重建 API、postgres、migrator 或自身。构建使用固定本地镜像 tag，操作 ID 仅用于持久进度，不再维护第二套部署 env 与镜像版本入口。
4. 模型、Qdrant 和同步状态卷使用显式稳定名称，可由非敏感部署变量覆盖。部署时先检查旧容器及卷归属，再停止旧知识写者并迁移到主项目；不删除数据卷或修改采集计划。内容网络纳入主文件，API/ONES MCP 可访问配置中的内容端点。
5. 执行器以相同宿主绝对路径只读挂载可信代码目录，并读取同一 `.env`；仅挂载知识服务需要的三个 Secret 源路径。默认从项目根目录执行，异地调用需明确 `KNOWLEDGE_DEPLOY_ROOT`。

## Risks / Trade-offs

- 默认启动需要更多内存/CPU → 沿用当前知识限制，避免迁移时重复运行两套推理进程。
- 旧项目残留同名 DNS 或共享写者 → 切换时精确停止并移除旧知识容器，保留卷，验证仅一个同步和 Qdrant 进程。
- 首次部署模型不存在 → 显式模型准备服务校验/下载固定模型，在线服务保持离线且只读；已有模型复用。
- 状态健康不证明工具可用 → 单独验证内部身份兑换、授权目录和实际检索；不读取或输出凭据及业务正文。

## Migration Plan

先完成合同测试及合成 Compose 解析，再核对真实卷、活动 Job/知识任务。停止旧同步和控制器，停止其余旧知识服务，保留数据；用主文件启动知识服务和更新 API/执行器，验证就绪与工具链。若失败保留现场与原卷，修复后继续，不自动改权限或重建空库。
