## Context

现有 Trigger 和 Delivery 分别持久化，运行时按入口类型在应用级投递列表中取值。钉钉要求全局唯一回复原会话，Webhook 要求全局最多一条结果投递，不能表达同一应用不同入口的独立去向。目标人员字段已存在于领域策略，但缺少 API 请求声明。

## Goals / Non-Goals

**Goals:** 修复 HTTP 保存；按入口准确配置、冻结、校验和选择投递；页面直接展示消息流向；防止删除、重排或修改入口后投递串线。

**Non-Goals:** 多分支工作流、同一入口多种投递、真实对外发送或自动激活用户应用。

## Decisions

1. 复用既有 Trigger 自然身份 `(trigger_type, connector_id, normalized_routing_key)`。Delivery 的 `config.trigger` 保存该入口引用，服务端统一规范化路由键并验证引用唯一存在；不使用数组下标作关联，不新增冗余 UUID 或数据库表。每个触发器至多一条 Delivery。
2. 新 Publication 使用 schema v7 并固定 `delivery_binding_mode=per_trigger`。管理校验、激活预检和实际接入使用同一套引用规则；运行时只取命中路由的 Delivery。旧不可变 Publication 保留已有执行规则，绝不把新配置缺失当成旧规则回退。
3. 页面按入口卡片配置去向，编辑入口时同步更新引用，删除入口同时删除其投递。钉钉固定回复原会话并自动使用入口连接器；Webhook 选择仅保存、钉钉私聊/群或高级 HTTP 回调。旧草稿中可唯一对应的投递在编辑状态转换；未使用或歧义配置显示明确提示并要求移除后保存，不默默分配收件人。
4. `target_user_ids` 是管理 API 正式字段，最多 20 人，发布前校验企业身份并冻结现有 recipient 事实。空人员表示只保存。
5. 保存失败展示在固定保存区，避免错误藏在很长的 MCP 工具列表下面。

## Risks / Trade-offs

- 自然身份随入口编辑变化 → 表单在同一更新中同步关联，后端拒绝孤立或重复引用；使用规范化键比较。
- 旧草稿存在不参与任何入口的投递 → 显示待处理配置，不自动启用、不将接收人分配给其他入口。
- 已有活动版本仍按旧规则运行 → 编辑后需用户自行保存、校验、发布和激活；不改写已有快照或真实业务消息。

## Migration Plan

无数据库结构迁移。部署 API 与前端；新客户端提交明确引用。旧活动 Publication 保持原有行为；新保存和发布全部采用显式关联。回滚必须恢复配套镜像，不允许旧代码接管新模式快照。

## Open Questions

无；用户已确认按每个触发器配置一个投递方式。
