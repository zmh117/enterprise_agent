## Context

本 change 基于 [proposal](proposal.md)，仅修改 `builtin-tool-resource` 与 `platform-operations` 的相关要求。

已核对的当前实现（Confirmed-current）：

- `KnowledgeSearch` 对授权知识库执行一次最多 200 点的召回；混合 profile 使用 dense / BM25 各 100 点和 RRF，其他 profile 使用 dense。`current_documents` 以最高块分数作为文档分数，最多保留三条证据，按分数直接排序。
- 在线服务在至多 50 篇文档范围内按需执行 ONES 可读性检查，满足 `top_k` 后停止。模型只收到引用、编号、分数和证据位置，最新正文另由 ONES 详情工具读取。
- `VectorRepository.evidence_many` 已读取、验证当前块的 `embedding_text` / `evidence_text` 及其 hash；其中 `embedding_text` 含标题上下文。既有知识读取账号已允许这些列，不需要新增全文权限。
- `KNOWLEDGE_USAGE_INSTRUCTIONS` 已通过工具描述及 Runtime system prompt 注入；没有代码所有的 0.15 过滤阈值，也没有文档级重排。
- MCP Manifest 的 `schema_hash` 目前只计算 input schema。仅修改 output schema 不会使旧冻结合同自动失效。
- `OfflineEvaluation` 调用 `VectorService.query(mode=auto)`，但报告固定写 `mode=offline_dense`；dense 离线候选初始数量还与在线固定 200 点不同，不能直接当成在线效果的严格对照。
- 在线 Embedding 已有独立 CPU 进程和 1 个执行、3 个等待的队列，排队/推理共用截止时间，取消请求不会提前释放正在计算的槽位。

上述事实来自当前源码，不证明线上部署版本、首次检索候选顺序或用户报告的过滤动作。历史重跑不能恢复首次检索证据。新增行为均为 Documented-intent。

## Goals / Non-Goals

**Goals:**

- 提升自然问法下已召回相关文档的前列排名，尤其是需要同时匹配多个症状的查询。
- 保持当前来源、版本、Job、知识库授权和 ONES 个人可读性边界，复用现有索引。
- 让工具分数、Agent 查询改写、核实停止条件和回答证据范围可检查。
- 建立可复现的基线/重排对照，将召回缺失、候选截断、重排失败和回答错误分别统计。

**Non-Goals:**

- 不训练或微调模型，不新增后端 LLM 查询改写服务、可配置模型市场或通用排序插件框架。
- 不在第一期修改 BGE-M3、BM25 分词、RRF 权重、分块 profile、数据收录范围或同步规则；不重建 collection。
- 不自动采集历史会话、生产日志、时间线正文或凭据作为评测集；不将聊天中的原始业务内容写入本 change。
- 不通过知识缓存替代最新 ONES 详情，不把相似结果或工作项已关闭等同于当前现场根因已经确认。

## Decisions

### 1. 在文档聚合之后、ONES 可读性检查之前重排

```text
Job / KB 授权与资源解析
  → 原始 query 编码 → 现有 dense 或 hybrid_rrf 召回（最多 200 点）
  → 当前块与版本校验 → 文档去重 → 原排序前 50 篇
  → 构造每篇至多 2 个候选块的输入 → 固定本地 Cross-Encoder
  → 依重排顺序检查当前 ONES 可读性（仍最多 50 篇）
  → 授权、资源与输入版本复核 → 最多 20 篇可读引用
  → Agent 读取最新详情并形成有证据边界的回答
```

沿用 `candidates.py` 的点身份、payload、当前 revision 和内容 hash 校验。文档候选仍按既有 `retrieval_score` 降序、`document_id` 升序取前 50；同文档重复块只占一个名额。重排不能找回这 50 篇以外的记录，评测必须单独揭示该限制。

从每篇既有证据中按检索分数、chunk ID 选择最多两个不同块，用它们已有的 `embedding_text` 构造一次 query/document 配对；同一文档只获得一个重排分数。采用现有带标题上下文的文本，避免扩大到未命中的任意全文。第一版每篇文档端最多 1024 个重排 tokenizer token，实际额度取 1024 与配对剩余空间的较小值；两块先平分实际额度，未用额度给另一块，按块顺序保留前缀。超长只裁剪文档端并记录截断计数，不截断 query。配对总长上限 4096 token（含特殊 token），query 不能留下有效文档空间时返回明确输入上限错误。文本选择、截断规则和这些初始参数均纳入 ranking profile，后续调整需重新评测。

重排按 raw logit 降序，平分时依次用 `retrieval_score` 降序、document ID 升序保证稳定。不得把 logit 做 sigmoid 后当作已标定的概率，也不设置新的相关性阈值。返回的 evidence 仍指向原始块位置/hash，不冒称重排窗口就是完整证据。

`ranking.py` 承担有当前调用者的候选块选择、请求准备和文档排序；在线 `KnowledgeSearch` 与离线评测共享这一逻辑。tokenizer、token 预算和截断实际执行归固定重排服务，Knowledge MCP 不加载模型或 tokenizer；两种调用消费同一服务/profile。内部文本对象不混入 MCP document DTO；响应只从允许字段显式构造。重排前已有 KB 授权，内部固定模型进程不对用户公开正文；最终引用仍逐条通过 ONES 个人权限校验。返回前重查实际送入重排的全部有界文档的 revision/块 hash，并复核资源和授权；漂移即失败，不输出基于过期文本计算的顺序。

候选为空时跳过推理，保持空结果语义。不可读候选从同一 50 篇池内继续补齐，不另外扩大召回。对用户返回的 `rank` 在可读结果内从 1 连续编号，不暴露不可读候选的名次空洞或数量。

选择理由：直接修复“已召回但排在后面”的环节，且不要求索引迁移。单纯扩大 top_k 或要求逐条读完尾部会增加回源成本，不能改善前列排序；改动 RRF 权重又不能直接表达两个症状的联合相关性。本期先保持召回可比较，若正确条目未进入候选池，再以评测证据提出召回变更。

### 2. 明确输出语义，并让冻结合同感知此次变更

业务输入仍只有 `knowledge_base_id`、`query`、`top_k`。输出变更如下：

| 字段 | 语义 |
| --- | --- |
| `retrieval_mode` | 实际召回方式：`dense` 或 `hybrid_rrf` |
| `ranking_method` | 本部署固定策略 `cross_encoder`；空结果不意味着执行过推理 |
| `ranking_profile_hash` | 固定模型、运行依赖、输入窗口和排序规则的摘要 |
| `documents[].rank` | 当前可读返回集内的最终顺序，1 起且连续 |
| `documents[].retrieval_score` | 原文档聚合检索分，只解释召回顺序，不代表最终顺序或相关概率 |
| `documents[].evidence[].retrieval_score` | 原候选块检索分，含义由 `retrieval_mode` 确定 |

删除两处旧 `score` 名称，不并存兼容别名。不向 Agent 输出重排 logit，内部评测可使用它检查排序。所有 identity、revision、number、evidence 位置/hash 及 `partial/partial_reason` 保留。`partial=false` 不代表全库覆盖；依赖失败不改成 `partial=true` 的成功响应。

为使现有输入 schema hash 识别此次输出与使用约定变更，仅在 `knowledge_search` input schema 根部添加固定 JSON Schema `$comment: knowledge-search-contract/v2` 版本注解。它不新增业务参数、不给 Agent 可选版本，也不改变全平台 hash 算法；部署时旧冻结 hash 与新合同不相容，沿用现有拒绝和重新发布流程。合同测试同时固定注解、输出 schema、描述与 Runtime 指令，防止只改输出漏升合同版本。

选择理由：无版本说明的数值容易被模型误用；只改提示词不能建立明确的响应语义。局部版本注解复用当前冻结机制，避免为两个输出字段引入全平台合同迁移。后续同类 breaking 变更必须同步升级注解并测试。

### 3. 查询与核实规则放入代码所有的 Agent 指令

- 对用户已给出明确问题，第一轮 query 保留原始症状、否定词、对象和已说明条件；清理寒暄不增加或删除业务含义。
- 某知识库第一轮核实后仍缺少同时符合关键症状的证据，且任务预算允许时，对该库最多补一次同义查询。不能把推测的网络、版本、位置或操作条件当成用户事实；每库最多两种语义问法，依赖重试不等于获得额外改写机会，且仍受总预算约束。
- 查询改写由现有 Agent 完成，不把语言改写逻辑放进 Knowledge MCP，不建立业务同义词硬编码表。服务端只对本次收到的 query 进行召回和重排。
- 多轮/多库结果以 `(source_id, work_item_uuid)` 去重。各次 query 的分数不直接相加或比较；跨库核实优先级依据问题对象与已读证据，不用分数大小决定。
- 按最终 rank 分批读取最新 ONES 详情；未找到足够证据时，在预算内继续检查尾部，不能只因分数低而跳过。找到足以支持回答的证据可以停止，但必须说明核实范围；预算结束或还有候选未读时，只能说已核实范围未发现，不能宣称全库不存在。
- 区分症状符合、已有记录描述的机制和现场根因。现场根因需要现场证据；同族记录、重排第一名和已关闭状态均不构成该证明。重跑不能证明首次候选顺序。

选择理由：此处已有工具描述和 Runtime 指令两个真实消费入口，使用同一份规则即可。仅把 top-20 全读一遍既不解决候选外遗漏，也不能约束查询漂移和回答过度推断。指令测试只证明规则被注入，真实遵循情况需要单独 Agent 验收。

### 4. 固定本地服务、独立资源、共同截止时间

固定型号采用 `BAAI/bge-reranker-v2-m3`（[官方模型说明](https://huggingface.co/BAAI/bge-reranker-v2-m3)）；Cross-Encoder 对 query/document 联合评分的使用方式参见 [Sentence Transformers](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)。2 核下长度分组后的长候选诊断耗时约 85.6 秒，BGE-base 对照约 15.2 秒。用户随后明确允许增加 CPU，优先保留大模型和长文本，因此采用 M3、8 核及原长窗口，base 只保留对照证据。人工补入标题的小样本不能代替人工冻结集和真实召回验收，详见 evidence.md。

新增 `services/knowledge_reranker/` 固定服务与 `RerankPort`，客户端只由 Knowledge MCP / 离线评测装配；不接受调用方传模型、地址或源码。API 包括健康/就绪/profile 和内部 `/rerank`：请求仅含 profile hash、query 和有界文档片段；响应是同序有限数值分数、profile hash 及有界 token/截断统计，不回显文本。请求/响应项数、hash、NaN/Infinity、缺项和多项必须校验。

初始边界：单次最多 50 文档、每篇最多 2 块、原始请求最多 1 MiB；推理微批最多 8 对且总 token 最多 8192，按 token 长度稳定分组，按 padding 后长度控制总 token；输出评分恢复原文档顺序。模型清单锁定 revision、文件摘要、tokenizer、dtype；依赖分别锁定支持的 amd64/arm64 CPU 环境。ranking profile 同时覆盖截断、候选/文档限额和 tie-break 规则。实施时从官方元数据生成并核对锁，不在提案中编造 revision 或文件校验值。

模型准备作为显式运维容器，完成后以只读独立 volume 供服务使用；运行服务离线，不暴露宿主机端口，不读取 ONES 凭据或平台主密钥。接入现有 `knowledge/compose.yml` / `knowledge/mcp.compose.yml`，不建立另一套独立知识栈。CPU 容器预算采用 8 vCPU、3 GiB 内存、8 个推理线程（2026-11-03 用户允许增加 CPU，优先大模型和长文本）；这是测量起点而非已通过的容量承诺。本机 8 核的 50 篇满长窗口合成压力在原 120 秒截止下超时；延长到 180 秒后的结果独立记录，正式 CPU 配额须按目标硬件和业务候选分布复测确定，见 evidence.md。

队列使用既有在线推理的 1 执行 + 3 等待语义，但与 Embedding 分开进程和槽位，避免离线索引/在线编码占用重排锁。共用同一请求的 `X-Knowledge-Deadline-Ms`，不重置 360 秒/Job 剩余时间；微批前后检查截止和取消。在计算中的取消不提前释放执行槽位，当前微批退出后再处理下一项。

明确区分 `knowledge_rerank_busy`、`knowledge_rerank_unavailable`、`knowledge_rerank_read_timeout`、`knowledge_rerank_input_limit`；非法响应或 profile 不匹配映射为稳定的重排依赖失败。任何失败不得伪装成零命中，也不静默退回旧排序。返回前复核仍使用剩余预算。

选择理由：独立固定服务符合已有本地模型边界，可复用其受限准备与截止设计；把两个大模型塞入同一编码进程会混合容量和故障边界。当前不引入外部付费 API、GPU 必需依赖或自动选择模型的抽象层。

### 5. 同候选对照评测与端到端验收分开

扩展现有 `evaluate_knowledge`，以一次召回得到的同一当前候选快照，分别计算原排序和重排结果。在线与评测共享固定 200 点、去重前后规则、前 50 文档和重排输入逻辑；不要另跑一次搜索后假定候选相同。对 dense / hybrid 实际模式如实标记，移除固定 `offline_dense` 标签。保留旧算法的排序作为评测基线，不把它变成线上可选后门。

评测前验证全部标签仍有效，记录 dataset/index/profile/代码和候选修订摘要；结束后校验快照未漂移。增量库对照以实际读到的有界文档修订/块 hash 为比较依据，不能只依赖不会随内容增长更新的索引身份。报告需覆盖：

- 200 点去重后相关文档覆盖、截取前 50 后的 `candidate_recall_at_50`，区分候选池没有目标与候选截断。
- 原排序与重排的 Recall@5/10/20、MRR@10、Hit@3，以及人工标注类别汇总。标签非穷尽时明确仅对标注集合计算；只按相关文档计算无法区分“精确症状”与“同族机制”时，人工先确定相应类别的正例，不把所有同族单据都标成正确答案。
- 编码/召回/重排/总检索阶段的 p50/p95、候选数量、窗口截断率和失败类别；有答案问题故障计零，不从分母移除；版本漂移使本次比较无效。
- 无答案问题的“检索返回候选率”仅描述检索行为，不称为回答误报率。系统没有标定的拒答阈值；是否错误断言存在匹配或已确认根因，必须另做 Agent 回源核实评测。

真实输入由有权人员准备经脱敏且人工复核的评测问法，开发夹具只用合成数据；生产原始问法可由用户现场复测，不由本任务从历史消息批量提取或持久化。普通输出只含汇总、阶段耗时、hash 和固定失败码，不输出 query、正文、原始异常、命中/拒绝工作项清单。人工复核的现场原问法和业务编号不进入通用日志。

第一批建议至少 50 条人工复核的独立问法，覆盖改写、复合症状、同族干扰、跨项目、长文本和无答案；开发调参集与冻结验收集按问题/关联工作项分组隔离，避免近重复问法跨集合泄漏。用标题自查询不能替代自然问法验收。

初始质量门槛：用户给出的已知漏排案例目标工作项 `#250449` 在现场原始问法下进入前 3；冻结集 MRR@10 相比基线提高、Recall@20 不下降；Agent 无答案/相似机制场景不得因新分数而增加无证据的确定性结论。该案例是验收目标，不在代码中硬编码 ID 或提升权重。若目标不在候选池，报告召回问题，不靠重排结果或改用标题问法掩盖。

目标机器上分别测单请求和四请求并发时的排队/推理/总调用时延、内存及失败；再用新 Publication / Job 验证真实 ONES 授权、最新详情、Agent 停止条件和端到端耗时。按用户 2026-11-03 的明确调整，任务的硬预算从 240 秒进一步改为 360 秒与 Job 剩余预算的交集；业务期望 p95 必须在目标环境评测前确定并冻结，不能见到结果后放宽。离线合成、真实模型离线、目标容器、真实 Agent 四类证据分别报告。

### 6. 可观测性和实现落点

安全审计继续使用当前 Job / MCP 调用关联、KB / 资源 / 索引版本与返回计数，可增加实际检索模式、ranking profile hash、重排执行与耗时/失败类别。内部候选身份和分数只在请求内或受限评测中处理，不向普通日志增加查询、块正文或不可读文档信息。

主要落点：

| 所有者 | 改动 |
| --- | --- |
| `application/search.py`、`candidates.py`、新增 `ranking.py` | 有界输入准备、重排、授权与版本复核、响应投影 |
| `application/ports.py`、基础设施客户端和 composition / MCP bootstrap | 固定重排依赖、profile 和错误/截止传递 |
| `shared/knowledge_tool_contracts.py` 及现有 Runtime 注入 | v2 输入注解、输出字段及统一查询/核实规则 |
| `services/knowledge_reranker/`、模型清单/依赖锁、知识 Compose | 模型准备、运行隔离、队列、健康检查和资源预算 |
| `vector_service.py`、`evaluation.py`、CLI、评测合同/手册 | 同候选对照、真实模式、指标/摘要与验收说明 |

## Risks / Trade-offs

- [CPU 重排可能超过时延或内存预算] → 先做真实模型单请求/并发基准；初始 50 篇和文本窗口纳入 profile。未达门槛不得声称完成部署验收，调整 profile 后重新跑同一冻结集。
- [前 50 篇截断或窗口裁剪可能丢失关键内容] → 分别测候选覆盖和截断率，包含尾部正例/长文本回归；不把召回失败归咎于重排，也不保证任意问法都能进入前 3。
- [缓存片段与最新 ONES 详情不一致] → 返回前核对当前本地修订，最终回答仍以最新详情为准；同步本身的覆盖限制不由重排消除。
- [新增依赖使在线请求更易失败] → 独立队列和截止、明确忙/超时错误、上线前目标负载测试；不以隐藏 fallback 造成结果不可解释。
- [新增调用和核实增加 Agent 用时] → 原话首轮、每库至多一次同义补查、跨轮去重和任务预算；记录详情调用次数和最终回答范围。
- [只改输出而冻结 hash 不变] → 固定 input schema 版本注解、旧快照拒绝测试和协调发布。
- [只对单个案例优化或把提示词测试当行为保证] → 分组独立验收集、近似干扰项和真实 Agent 核实测试；保留未达成证据。

## Migration Plan

1. 先实现同候选评测和合同/合成回归，准备并验证固定模型文件；不改当前索引、不迁移数据库数据。
2. 完成离线真实模型比较，在目标硬件冻结时延预算并测 CPU / 内存 / 并发；达标后才能安排上线。仅模型健康或合成测试通过不满足此条件。
3. 准备新模型 volume 和镜像，协调 API / Runtime / Knowledge MCP 的合同版本；按现有运行管理流程排空使用旧知识合同的任务，不改写其快照。
4. 部署重排服务与知识 MCP 接线，校验 profile / ready；对受影响 Agent / Application 通过既有发布流程产生新合同快照，使用新 Job 做真实 ONES 验收。知识资源和 collection 身份不因排序模型改变而重建或重新发布。
5. 回退时协调恢复前一版本的服务镜像及匹配的工具发布，保留索引、文档与模型卷；不在同一新合同下静默切换旧排序。上线/回退操作不属于本次 proposal 的执行内容。

## Open Questions

- 用户确认 3 GiB 内存，并允许增加 CPU 以保留大模型和长文本；当前采用 8 核；尚未设定业务 p95 门槛，暂无人工标注集，并授权使用本地 PostgreSQL knowledge 数据做诊断。先测受限容器和有界候选；部署验收前必须冻结 p95、并发和人工标注条件。
- 人工复核的调参/验收集及真实 ONES 测试身份由有权人员提供；没有这些输入时可以完成代码和合成验证，但质量及真实环境任务保持未完成。
- 固定模型在本领域和目标 CPU 上是否满足门槛需要实测；若失败，记录失败原因并评审后续模型/窗口调整，不能在本提案中预填通过结论。


## 360 秒请求的在途身份续期（2026-11-03 用户明确确认）

Business Principal 的 canonical TTL 上限仍为 300 秒。Knowledge MCP 在重排后需要重新验票，故 360 秒计算预算本身不能保证长请求完成。新增固定的内部知识 Principal 续期入口：必须同时提供 Knowledge Service Principal 和尚未到期的 knowledge-mcp Business Principal；无可覆盖的 job/server/scope 参数。平台复核当前 Job、用户、Publication、冻结 scope/authorization hash 和实时权限，再为同一绑定签发最长 300 秒的新票据。除 jti/iat/nbf/exp 外声明必须完全一致；过期旧票据不续期。

Knowledge MCP 为每个 tools/call 建立仅存在于内存的票据持有者，到期前有界后台续期，后续鉴权、连接凭据桥和 ONES 可读性桥使用当前票据。续期继承原始调用截止和取消信号，单次续期最多 5 秒，不重试、不重置检索预算、不重放模型请求。续期失败使原调用失败关闭，执行中的模型请求按既有取消链停止；请求结束时停止并回收续期线程，清除内存引用。不增加数据库表、通用租约层或 Agent 可调用的刷新工具。

撤权、Job 结束、绑定变化、跨用户/Job/Server、续期响应错配均须拒绝；Service Principal 本身沿用既有按需短期续期。安全审计只记录固定事件/失败码及既有安全关联，不保存票据或查询文本。
