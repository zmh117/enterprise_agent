## Context

### 已确认范围

- 用户确认三个来源属于同一项目 SVN 仓库、同一分支：`set_server` 是后端，`set_web/EBR` 是工厂端前端，`set_web/JTH` 是集团端前端。角色用于定位界面和业务适用范围，不代表三个独立产品版本分支。
- 当前本地 `ones知识库/项目代码/` 为首次知识基线。当前没有可核实的 SVN URL、分支相对路径或 revision；这些属于上线配置，不能用本项目 Git HEAD、本地文件时间或目录名称代替。
- 工厂端首期为工单发布、开始、报工，以及它们实际依赖的处方、主配方、物料、系统配置、权限和公共校验。集团端首期为应用启停、授权范围及对应后端依赖。其他 EBR/JTH 业务属于未覆盖内容；其他前端目录不纳入来源。
- 本次实现先提供规则解释、版本比较和变化追溯，同时记录未来诊断需要的数据项；不读取现场工单实例，不自动认定现场根因。

## Goals / Non-Goals

**目标：**

1. 用当前本地代码完成可审查的提取、导入、检索问答和更新闭环。
2. 保存对象各自的状态机、操作条件和跨对象依赖；每个重要结论能定位到对应来源版本代码。
3. SVN 接通后每日增量跟进，支持精确历史版本和非单调规则变更；保留失败恢复与旧快照服务。
4. 使用现有基础设施和 Python Runtime，普通用户按现有 KB 授权查询，源码访问仅授予提取作业。

**非目标：**

- 全 MES 一次性覆盖、全历史逐提交全库重跑、静态分析完整性证明、通用规则执行引擎。
- 图数据库、独立状态机运行引擎、另建模型执行服务、任意插件/Shell、直接查询生产数据库。
- 普通问答返回源码全文、集团/工厂实时数据诊断、自动识别所有现场部署、SVN Hook、跨仓库协调。

## Decisions

### 1. 来源基线有独立身份，SVN 关联必须有证据

首次导入由部署 CLI 接受管理员明确指定的来源根目录；Web 仅选择已登记的来源/产物 ID，不接收任意宿主路径。读取允许的代码、接口/表结构定义及非敏感配置定义，排除真实配置、凭据、业务导出、日志、依赖缓存、二进制、生成产物及其他前端目录。通过导入策略处理敏感内容，未通过准入的材料不会进入 Agent、知识包或索引；相关知识标记依赖未获准访问。

实施时冻结不可变来源清单：组件角色、相对路径、文件摘要、编码、字节数、纳入/排除依据、扫描完整性。C++ 的 GB18030 与 Vue/JS 的 UTF-8 分别解码，证据行号按声明解码规则计算，摘要以获准原始文件字节计算；如存在准入转换，另存转换后摘要及版本，不能混称原始源码。使用前后校验摘要避免边提取边变化。提案本身不创建全量源码副本，也不声称已完成首次冻结。

来源引用是区分联合：`local_bundle(bundle_id, manifest_hash, svn_revision=null)` 或 `svn(repository_uuid, branch_path, revision, manifest_hash)`。本地基线可独立发布查询，界面和回答明确显示“本地基线，SVN 版本未确认”。

接通 SVN 后，绑定已核验的仓库 UUID、分支和三个组件相对路径。对管理员提供的候选 revision，按同一范围和已声明的字节/换行规则逐项核对清单，只有一致才增加本地基线到该 SVN 快照的验证映射，不改写原本地来源记录。无法匹配时保留本地基线，选择一个明确 SVN revision 重新建立 SVN 起始快照；跨两者可以比较内容，但不能宣称差异来自某次提交。首次可记录的 SVN 历史下界单独展示。

备选方案是直接把当前本地代码标为 SVN HEAD；拒绝该方案，因为本地包可能混合版本或含未提交改动。

### 2. 知识单位采用显式状态迁移和规则，关系按版本保存

2026-11-06 核验发现上一版虽然保存 states/guard/effects，但没有来源状态到目标状态的迁移结构，且跨单元对象身份漂移。因此原 v1 不视为状态机交付；本节及第 10 节替代原有宽松数据合同，历史失败证据不改写。

知识种类改为服务端生成的 object 身份节点、模型提取的 transition 和 rule。模型不能输出对象身份定义或旧 operation/state_machine 标签。每条 transition 必须属于明确 object_key、machine_key 和 event_key，具有来源状态选择、guard、有顺序和稳定 action_key 的动作、成功目标、成功确认点以及失败条件/阶段/结果/剩余状态/已保留动作。纯校验或不改状态的操作用显式 unchanged 迁移，不伪造新业务状态。

来源状态选择只接受明确 states 集合、经证据证明没有状态门槛的 any，或 unresolved；目标只接受确切 state、unchanged 或 unknown。未知状态、未知失败结果和未解析守卫阻止激活。异步请求受理若尚未发生状态变化，必须表达 unchanged，并与后台实际执行的迁移分开；不能把受理成功写成 Working。失败发生在提交后时保留已提交动作和实际可证明状态，不能默认回滚到起点。

知识身份使用稳定业务键和 UUID，不以文件名、行号或内容摘要充当永久身份。每个工作单元只写本入口命名空间内的迁移和规则，共用对象身份来自固定目录。重命名由旧身份、接口和业务证据核对；不确定时产生待确认映射，不自动合并。

不可变修订至少包含：

| 内容 | 必须保留的语义 |
| --- | --- |
| 适用范围 | backend/factory_frontend/group_frontend、对象/操作、源码来源、构建条件和配置条件。 |
| 状态与条件 | 原始值及显示含义；AND/OR/NOT、短路和检查顺序；空串、NULL、缺失等按代码区分；复杂表达式保存有证据的描述及未解析项，不执行任意表达式。 |
| 结果 | 请求受理、实际执行、状态写入、事务提交、消息与回执分别描述；拒绝/失败/部分完成/未知均有依据。 |
| 证据 | 每条条件/动作/结果引用 source_snapshot_id、相对路径、符号、真实行范围、文件摘要及证据片段摘要；普通读取不返回原始源码正文。 |
| 数据需求 | 未来诊断需要的字段、关系路径、时间语义、来源候选及核实状态；不内嵌现场实例数据。 |
| 覆盖 | 入口 analyzed/partial/not_analyzed，未解析调用/条件编译/宏/动态 SQL/外部实现、核验范围和遗留问题。 |

关系种类包括对象引用、包含、操作依赖规则、规则依赖源码/配置、动作影响对象。处方物料明细独立表达其用量/单位等使用属性。关系保存读取时点及 `fixed_version/current_record/copied_at_operation/unknown` 方式；关联关系不能自动推出操作会读取该对象，也不能自动推出限制传递。

每份代码知识快照固定知识修订与关系集合。前端限制、后端行为、需求意图、运行观察分开；代码中不存在的行为、编译关闭分支或注释不能作为确定实现。未覆盖操作不能从“没有找到拒绝条件”推成允许。

备选方案是把工单、处方、物料合成一个巨大的状态机或嵌套 JSON 副本；拒绝该方案，因为它会重复规则、放大状态组合并丢失独立版本。

### 3. 复用知识身份和存储，增加明确的代码版本职责

- 复用 `knowledge.source/document/document_revision/knowledge_base_document` 管理身份与不可变修订；迁移本体采用 `code-business/v2` JSONB 合同，同一事务同步到有外键的状态机关系表。关系表必须能直接查询某对象的状态、事件和出入迁移；不能只把摘要存成文档而要求查询模型补全迁移。
- 补充以下职责，按关系和事务需求落表，不另建第二套 kb_item/kb_revision：

| 职责 | 关键身份及约束 |
| --- | --- |
| 代码来源绑定与来源快照 | source_id + 配置修订；不可变本地包或仓库 UUID/分支/revision/清单；可保存经过核验的映射。 |
| 提交账本 | 仓库 UUID + revision + 范围配置修订唯一；记录路径动作、复制来源、属性变化、采集完整性及分析状态，提交说明不作为规则事实。 |
| 构建及工作单元 | build_id、固定父快照/目标来源/Agent Publication/提取合同/模型配置、去重键、租约、阶段、Job 和候选 Invocation 产物清单引用。 |
| 知识快照及成员 | snapshot_id 固定 document_id → revision_id 和关系；可用性、索引清单及覆盖状态可核验。 |
| 版本化关系及反向依赖 | 快照内对象/规则关系；修订的源码路径/符号、配置与结构定义依赖可索引，不以可变全局关系覆盖历史。 |
| 规则差异和历史分析 | 同知识身份的旧新修订、结构化差异、证据、目标 revision 或未决范围、已检查的提交区间。 |

- 代码读取通过 snapshot_member 连接修订；不能使用全局 current_revision_id 代替目标快照。ONES 继续按当前修订和既有收录语义工作。
- Qdrant 复用服务，每个代码 KB 使用固定集合，point ID 包含 snapshot_id/knowledge_revision_id/chunk_id/profile_hash；按不可变内容摘要复用 Embedding 计算，首期允许相同向量在不同快照的点重复存储以换取简单可靠的版本隔离。服务端注入 snapshot_id 和 KB 范围过滤，命中再回 PostgreSQL 复核成员、修订与当前授权。
- 候选点可写入但只能通过已就绪快照被查询。内容源为 PostgreSQL；Qdrant 不承担规则事实与版本发布事务。
- 按用户确认，代码知识流程不使用 File Service。采集器把获准代码冻结到部署登记的来源卷，按 source_snapshot_id 建立不可变目录和清单；Runtime 以只读方式挂载来源卷，不能映射正在 svn update 的可变工作副本。后端 GB18030 可生成 UTF-8 阅读表示，保存原始/表示摘要、编码和真实行号。只有绑定该快照的受管提取 Job 能读取允许路径；普通 Job、其他快照、符号链接和绝对路径逃逸均拒绝。
- 提取 Agent 使用既有 SDK 的 Read/Glob/Grep 阅读获准快照，Write/Edit 只允许本 Job 的候选输出目录。Runtime 在每次文件操作时校验受管 Job、当前服务账号/应用授权、来源配置及路径摘要；禁止 Bash、Shell、网络拉取和源码写入。这个来源授权来自服务端构建/Job 绑定，不从用户消息或模型参数取得。
- Runtime 在模型执行完成、沙盒清理之前，将固定 outputs/candidate.txt 与 outputs/report.md 回收到独立持久产物卷。产物目录由服务端 Job/Invocation 身份确定，使用原子提交清单绑定 build/unit/source_snapshot/config/request_digest、内容摘要和大小；Worker 只读该卷并验证归属，不接受模型提供的宿主路径。重放复用同 Invocation 产物，未知执行结果不能启动重复提取。
- 候选采用 code-business/v2 JSON envelope，仍包含六个逻辑 JSON/JSONL 条目，单包仍有 15 MiB 上限。v1 包直接拒绝，不能从其自然语言推断迁移后自动转换。来源卷与产物卷的清理由专用代码知识维护控制器按明确保留和活动引用执行；已激活知识仍以 PostgreSQL 为准。原始来源已清理时证据位置仍可查，但不能声称仍能逐字复验；重新提取须新建导入并核验摘要。

首期使用 PostgreSQL 有界关系查询，不新增图数据库。证据与条件树放修订 JSONB，只有确有查询需求的关系/依赖建立索引。

### 4. 提取复用标准 Python Agent Job

来源采集器负责 SVN 客户端和只读快照，部署时固定访问地址与受管 Secret 引用；认证材料不进入 Agent 输入。提取运行在现有 Python Runtime，通过专用的已发布提取 Agent/Application 与受限服务账号执行，默认不启用外部消息交付。

新增受管内部 Job 入口复用标准 Job 创建事务、Outbox、Publication、身份、Runtime、预算和审计；每个工作单元冻结 build_id、source_snapshot_id、allowed_scope、提取合同及配置摘要。关联存入服务端构建/Job 绑定，以 Job ID 核实；不把客户端额外字段塞入 Runtime 协议或由模型传参授予读取权。内部路由显式使用无外部交付类型，不能继承默认钉钉回复路由。长构建拆成多个持久工作单元，每个单元独立有界，不通过延长或重置同一个 Job 截止来跑全库。调度器/Worker 不加载模型 SDK，不直接绕过 Runtime 调用模型。

提取 Agent 使用 Runtime 的固定 SDK 文件工具与只读来源挂载。来源卷根目录来自部署配置；服务端以 Job ID 查验构建/单元授权，解析确切 source_snapshot_id 和允许文件集。不得把整个宿主仓库作为普通 Job 的可读目录，也不把所有快照作为模型可自由选择的范围。Read 每次最多 400 行/64 KiB，Glob/Grep 最多 100 个定位项；写入仅允许本 Job 产物目录。该通道不需要知识 MCP 或文件 MCP 的人类账号权限豁免。Runtime 使用可选固定 Service Principal code-knowledge-runtime 向平台元数据入口复查，只有 Job/Invocation/request_digest 与当前租约、账号、Publication、应用权限均有效才返回既定范围；不增加 Runtime 对 Job/RBAC/知识表的数据库权限。提取运行审计保留身份、状态、用量和工具事件元数据，不采集 SDK 消息或原始模型 API 正文；候选和源码正文仅保存在受控卷和经校验的知识修订。

一个工作单元：定位入口 → 读取完整相关函数及必要上下文 → 沿允许范围追踪依赖 → 输出结构化结论和证据 → 在限定输出目录生成候选产物。文件和上下文超过现有限制时拆分单元，不能把整个仓库塞入单个会话或突破文件工作集上限。发现范围外的合法业务依赖时输出扩展请求，由确定性调度器在配置允许范围内创建后续单元；模型不能自行扩大范围。

模型编写有固定 Schema 的 JSON 对象，entries 以逻辑文件名为键，证据 excerpt_hash 固定为 null。Runtime 核对允许范围、文件摘要及行号后补齐证据片段哈希并生成规范封装，各条目摘要均由代码计算，Worker 仍独立校验；不要求模型手工计算哈希。标准候选包的逻辑条目为 `manifest.json`、`knowledge.jsonl`、`evidence.jsonl`、`relations.jsonl`、`coverage.json`、`changes.json` 和人读 `report.md`；通过 Runtime 受控产物回收使用上述 JSON 封装和独立 Markdown 报告，离线导出时可恢复逻辑文件布局。模型输出不是发布命令；校验器重新核对身份、文件摘要、行号、引用和范围，并对受影响业务样本执行检查。未完成关键依赖的既有确定结论不得进入可激活候选。

源码、注释、提交说明和候选解释均是不可信内容。提取 Skill 不得改变工具授权或发布策略。普通问答 Job 即使选择提取工具也必须因缺少受管提取授权而拒绝。

### 5. SVN 增量以固定 revision 和依赖范围驱动

实施选择：首期采用完整业务范围重建，合并旧知识身份/反向依赖与新入口/引用导航。增量粒度目前是提交账本和固定目标调度，不是任意函数级自动复用；共享配置、结构和校验变化都会进入重建范围。缺失旧知识必须作为带证据的明确删除并经过独立核验，否则阻止激活。真实模型耗时和成本尚待验收，后续只有在准确性与覆盖有证据后才考虑缩小提取范围。

同一仓库 UUID、分支与配置修订作为来源流；三个组件在一次 SVN 构建中使用同一目标 revision。有效分支中的 revision 有间隔是正常情况，记录检查过的仓库区间及实际相关提交，不能按日期或无关提交填补内容事实。

1. 每日计划默认 Asia/Shanghai 02:00，管理员可配置；接入参数未验证时显示未配置，不启动网络采集。启用后首次执行显式基线/对账，暂停仅阻止后续调度。已有任务时合并后续待构建目标，保留全部提交记录。
2. 每轮开始固定目标 revision，获取上次采集游标之后的变更路径、内容差异、属性/复制来源和清单；SVN 输出使用机器可读格式。分支外的合并提交只有实际进入选定分支后才影响知识。
3. `collected_revision` 只在变更记录和后续待处理事实可靠提交后推进；`active_snapshot_id` 表示查询已验证内容，二者独立。失败重试复用固定目标，不能把新 HEAD 混入原任务。
4. 结合旧反向依赖与新代码入口/引用扫描确定影响范围；公共校验、枚举、配置默认值、宏和结构定义变化触发相关范围复核。依赖不清时扩大模块重建，无法在预算内完成则保持未完成，不能静默裁掉依赖后发布。
5. 删除、替换、移动、复制与普通修改分别处理。知识缺失只有完整范围扫描和删除证据支持时才移出新快照；移动经身份核验后复用知识 ID。定期重扫入口/依赖清单，补充新增调用，扫描频率由同一运维计划配置，不另建调度系统。
6. 业务需要的 `svn:externals` 纳入显式依赖清单，固定实际解析 revision 和属性摘要；未固定 external 的独立变化需要被采集器核对，即使主仓库 revision 未变。首期不能解析的外部依赖阻断相关完整性声明，不扩大为跨项目编排。

不采用每日读取提交说明并直接改自然语言知识，也不要求每个提交重建整个仓库。

### 6. 历史版本与变更时间采用精确证据

区分业务对象版本、SVN 源码版本、知识修订和知识快照。每日更新形成目标版本快照；正式发布版本由管理员提交精确 revision 预构建，发布版本准备不代表现场已部署。现场版本绑定只接受明确配置，本 change 不做自动现场发现。

记录每个范围内提交的变更元数据和历史分析状态。历史查询使用目标 revision 的源码与当时依赖；未提取目标返回 `BUILD_REQUIRED/BUILD_PENDING`，不得替换为相近版本或最新快照。没有 SVN 来源绑定、目标不可读或超出可证明范围时明确 `VERSION_UNAVAILABLE/BASELINE_UNMAPPED`。

已授权历史查询产生的后台工作作为派生缓存构建需求：查询服务在短事务中幂等登记需求，由已启用来源计划和受限提取服务身份处理；仅复用已发布来源与已批准范围，不允许创建来源、扩大权限、激活开发指针、改变现场绑定或产生外部业务写。该内部派生行为在工具合同明确声明并受配额约束，不借只读工具启动任意管理操作。来源未启用按需构建则只返回 BUILD_REQUIRED。初始默认每来源最多一个活动构建、20 个待处理不同版本，重复请求返回同一需求；管理操作可以重试，查询不无限轮询。

版本比较按同一 knowledge_id 比较来源状态、guard 树、检查次序、动作、结果、适用配置和关系。条件没有改变但证据移动属于 evidence_only；关联未确认则返回 identity_unresolved。关键词变化或摘要差异不足以证明业务放宽/收紧。

历史追溯按相关提交及固定版本源码核实，记录检查区间的连续性；不能用二分法假设规则单调。`r100:拒绝 → r101:允许 → r102:拒绝` 必须能恢复两次变化。若仅核实两端，返回未决 revision 范围，不能把终点称为首个变化提交。按需分析可分批续做；每日端点相同不删除中间提交线索。首次基线之前的历史仅在 SVN 可访问且对应依赖可重建时按需支持。

### 7. 候选校验、索引就绪和激活分别推进

构建阶段：`QUEUED → SOURCE_READY → EXTRACTING → VALIDATING → INDEXING → READY → ACTIVATED`，失败、中断、取消独立保存；历史构建到 READY 即可查询，不自动推进开发 active 指针。每个阶段和单元有幂等键、持久结果、原子领取及租约版本。

校验覆盖来源稳定性、引用完整性、知识身份、关系闭合、已声明范围的入口完整度、关键未知项和业务问答样本。首批样本至少覆盖工厂端操作及其跨对象条件、集团端启停授权、前后端差异、受理与成功、配置分支和版本反转。固定样本由人工核对源代码建立预期，不能让同一次提取模型同时生成答案并自行宣布通过；真实业务抽查仍单独记录。

预期点 ID/数量/摘要与 Qdrant 可见性验证完成后，标记 READY。激活在 PostgreSQL 事务中比较父快照、构建租约和当前来源配置再切换指针。迟到任务不能覆盖新快照，半完成 Qdrant 写入不影响旧快照；重试使用确定点 ID。快照可查询性与来源资源发布/KB 授权分别管理。回滚只切换到完整可用快照；没有可用旧索引时报告不可用，不能回滚到半成品。

新知识快照不修改资源 Publication。首次接入、新工具或来源/模型/分块配置改变仍按现有发布合同重新验证；ONES 文档继续逐篇增量生效，不套用代码快照的整体切换策略。保留已支持历史版本，首期只清理明确失败且无引用的候选；清理完整历史快照必须成为显式后续运维决策。

### 8. MCP 合同采用同一服务和明确版本

目录和搜索扩展采用版本化 schema，不改写历史冻结合同；原 ONES 分支继续返回既有文档字段和访问模式，新增 `source_kind` 区分代码分支。一个代码 KB 绑定一个来源流及明确授权范围，不把 source_id 或用户提供的 revision 当权限凭据。

| 工具 | 输入要点 | 输出与用途 |
| --- | --- | --- |
| `knowledge_list_bases` | 原有有界游标 | 增加来源类型、组件角色和可选版本方式的安全摘要；无正文、文档计数、SVN 凭据或内部地址。 |
| `knowledge_search` | 原有 KB/query/top_k；代码来源需要 version_selector | 返回固定 snapshot_id、source_ref、知识 ID/修订、匹配片段和证据定位；缺少版本返回 VERSION_REQUIRED；未就绪返回显式状态/需求 ID，无伪造空命中。 |
| `knowledge_get_behavior` | KB、snapshot_id、knowledge_id、可选依赖页游标 | 完整操作/规则、依赖关系、证据、coverage/unknown；对象节点可列出完整或有界分页的操作集合，不能以向量 Top-K 代替完整操作清单。 |
| `knowledge_compare_behavior` | KB、knowledge_id、mode=compare/history、from/to selector（history 下界可省略） | 两版本结构化变化，或给定上界内的变化列表；返回已核实区间、未决区间、证据和精确 revision 的证明状态。下界省略时只使用该来源可证明的历史下界。 |
| Runtime Read / Glob / Grep | 服务端提取 Job 绑定的只读来源目录、允许路径及有界范围 | 只读取该不可变源码快照；普通 Job 无此挂载访问授权，Write/Edit 仅用于本 Job 候选产物。 |

version_selector 仅允许 `{kind:local_baseline,snapshot_id}`、`{kind:svn,revision}`、`{kind:latest_verified}`。latest 必须来自用户明确请求；解析后固定 snapshot_id，后续读取不随指针变化。查询结果同时区分 requested_source_revision、实际快照来源和历史核验状态；同一内容复用到多个 revision 需要完整差异/依赖证明，不能根据快照日期插值。

单次读取沿用 360 秒及 Job 剩余预算较小值，总响应不超过 512 KiB。搜索 top_k 1–20；完整操作本体不静默截断，依赖按最多 50 项/页分页，默认最多展开 3 层/100 节点，循环去重并返回未展开引用和原因。不能在必要条件未展开时宣称操作已完整解释。源码读取每次最多 400 行/64 KiB，搜索最多 100 个定位项；超长行或超限结果明确标记 partial，不能让截断破坏证据行号。

代码来源采用现有用户/角色/应用 KB 权限与受管来源授权，不要求 ONES 绑定，也不通过切换全局 offline 绕过 ONES 权限。返回前复核当前授权、KB 收录、快照可查询性、成员和索引；授权撤销仍拒绝历史快照。普通工具证据仅包含解释、标识和代码位置；源码正文仅能进入受限提取 Job 的内容/审计边界。

### 9. 两个 Skill 和管理体验

在 `.claude/skills/` 增加提取和问答 Skill，注册到现有 SkillLoader/发布校验，两个 Skill 只能进入明确选中的新 Publication，不能加入默认历史配置。

- `extract-business-knowledge`：按照固定包合同从源码提取、检查 guard/成功边界、追踪实际依赖、保留未知，输出候选文件；不得提交数据库或激活知识。
- `code-business-query`：先发现获准知识库；版本缺失时询问，已有明确会话版本或部署绑定则核实并显示；用户指定 SVN 版本不支持时报告事实，不自动改用本地/最新；普通问题读取完整操作与必要依赖，变化问题调用比较/历史工具。
- 工厂端、集团端、后端为适用角色；例如“应用权限”需区分 MES 集团端授权与 Enterprise Agent 平台权限。含糊对象先澄清，不能把两个系统同名概念合并。
- 状态、版本、证据、适用条件、未确认项进入最终答复；向量分数不是可信度，源码规则不是现场根因证明。

管理界面延用知识运维入口，分开展示来源配置/启停与知识资源发布、当前本地基线、SVN 映射、每日计划、已采集/已激活 revision、各组件覆盖、构建及历史请求状态。配置使用受管 Secret 引用；读写和重试/激活遵循现有权限与审计。网页显示持久阶段/实际计数，模型分析期间没有可靠总量时不展示虚构百分比。

### 10. 状态机 v2 的身份、落库与重建

服务端维护一个代码受管的 MES 身份目录，固定本次范围的对象键、状态维度和事件键，例如 `factory.work_order` / `factory.work_order.lifecycle`，以及发布、开始受理、开始执行、报工预检和报工确认事件；集团应用有独立命名空间。目录只声明身份和归属，不预填允许状态、条件或迁移事实。目录摘要进入处理配置和 Job 合同。新增对象需改目录并重新发布；模型遇到目录外对象只能记录未知，不能自动注册别名。处方、主配方、物料、处方物料明细、工单运行期物料分别有身份，避免把用量写成物料主数据属性。

对象身份节点由控制器确定性生成并标注 identity 事实类别；不声称从源码发现状态或行为。模型候选只含本工作单元命名空间下的 transition/rule，可通过关系引用目录中的共同对象。由控制器建立对象包含迁移的关系，防止模型漏连；对象节点的来源版本和可查询性仍由快照成员约束。

| PostgreSQL 表 | 核心职责 |
| --- | --- |
| code_object | 同一快照内共同对象键及其 document 身份 |
| code_machine | 对象的明确状态维度；前后端值不能混成同一维度 |
| code_state | 状态机中的稳定 state_key、原始值和显示名；同一原始值不能被不同键重复声明 |
| code_event | 目录固定的事件与所属对象 |
| code_transition | 确切 document/revision、对象/状态机/事件、来源选择模式、目标模式/目标状态、guard、顺序动作及成功边界 |
| code_transition_source | 明确来源状态集合，对所属状态机建立外键 |
| code_transition_failure | 失败分支身份、发生条件/阶段、拒绝/失败/部分完成/未知、剩余状态、保留动作及证据 |

状态机行、迁移行及快照成员必须在同一事务写入。状态引用不存在、属于别的状态机、同键含义冲突、同原始值多键、失败引用不存在的动作或对象别名均拒绝；不同工作单元相同状态定义的证据可以不同，身份/原始值必须一致。后续单元输入已有状态定义，复用其键，不从中文标题猜测相同对象。完整 JSON 修订与关系表是同一次受校验提交的两种读取形态，不能独立修改。

失败后状态区分 `unknown`（提取证据不足，阻止启用）与 `indeterminate`（已读到错误/补偿失败分支，源码本身不能保证最终状态）。后者只允许用于失败结果，必须有分支证据、明确已知的 failed/partial/rejected 结果以及未来现场核验字段；不能用于成功目标或掩盖未读实现。独立核验必须确认这是已证明的运行时不确定性。一个错误条件下补偿成功与补偿失败必须分别建失败分支；正常返回但提前结束且没有状态变化的路径必须另建 unchanged 迁移，不能与完整发布成功共用目标。已应用 155 后用新的 forward migration 扩展此状态模式。

模型在 Write 候选前已能得到结构与引用失败的明确反馈。关键条件、动作及失败分支必须引用对应源码证据，非空 evidence_id 只证明可追溯，不证明语义正确。独立核验继续检查具体分支、默认值、检查顺序、事务和调用链；对发布/开始/报工及集团三个入口逐项记录结论。额外导航包含真实的协议分发、枚举和 MDMat 报工实现，不能以授权内搜索漏读为成功覆盖。

状态机成功边界必须区分主记录、缓存、状态历史和通知。独立异步回调通过固定事件建模，开始工单目录包含 `request`、`execute` 和 `status_changed`，不能把请求返回或写历史当成主记录状态落库。依赖缺失的关键性按候选实际主张判定：未准入的权限内部算法可以是明确未覆盖，但只保留调用点能够证明的检查函数和返回码条件；涉及所主张状态、动作或失败结果而尚未查清的依赖仍阻止启用。不得为了通过验收降低未知项等级。

详情和管理页面显式展示“对象 / 起始状态 / 事件 / 条件 / 动作 / 目标 / 失败结果”，状态列表不能替代迁移表。规则历史比较纳入 object_key、machine_key、event_key、来源/目标模式、动作顺序和失败结果，来源位置变化单独归类。Qdrant 仍只作检索投影，业务事实和图关系以固定 PostgreSQL 快照为准；不引入图数据库或生产状态机执行引擎。

用户已授权旧候选不兼容。采用新的 forward migration，不改写已应用的 154；先核对目标代码来源没有未停止 Invocation、没有已就绪快照和索引引用，再按 source_id 清理旧候选成员、关系、依赖及代码 document/revision。保留源码基线、终态 Job、构建元数据及独立核验报告，保留 ONES 内容/索引/授权和凭据。新构建固定 v2 及身份目录摘要，旧构建不可恢复为 v2；清理前后输出仅含身份/数量/摘要的核对记录，不输出源码或认证材料。

## Risks / Trade-offs

### 当前 Agent 直接审校入库（2026-11-06 用户调整）

停止额外模型 API 提取后，当前 Agent 可以在获准冻结源码上直接编写 v2 审校知识包。部署 CLI 验证管理员、原失败构建及候选摘要、所有相关 Invocation 已停止、源码清单和逐项行证据、六入口覆盖及当前身份目录，创建新的候选构建和不可变修订。审校包内容摘要、原构建/候选摘要、审校人、报告引用保存在构建配置和审计中；没有 Runtime Job 的修订不得冒充 Runtime 原始输出。原模型包、Job 和失败快照保留。输入幂等、验证和入库必须原子，失败不能留部分对象或状态。导入不审批、不调用模型或 Embedding，不索引/激活，仍须经过已有启用门禁。

真实代码表明组态工单 STATUS 与运行期工单 STATE 独立变化：发布请求提交组态 20 后，运行期先创建为 10，再由后台 WoPublish 推进到 20；开始回调再推进运行期状态。目录因此区分 `factory.work_order.configuration` 与 `factory.work_order.execution` 两个机器，仍共享 `factory.work_order` 对象。事件固定所属机器，发布的 request 对应组态、execute 对应运行期；开始和报工属于运行期。不能因为原始数值相同就把两个状态维度混成一个。前端组合读取规则单独有证据记录。

- [本地包没有 revision] → 首期保留诚实的 local_bundle 身份；线上同步允许新建已知 SVN 起点，不强行匹配。
- [C++ 宏、动态分发或外部实现导致依赖不完整] → 入口/写入扫描结合 Agent 追踪；保留 unknown，扩大模块范围；关键影响未核实不激活。
- [每日端点相同掩盖中间变化] → 持久提交账本和非单调历史分析；明确连续核验区间，不用端点差异冒充完整时间线。
- [模型输出合法但业务错误] → 逐事实证据、固定人工核验样本、真实业务抽查，测试通过不表述为形式化正确性证明。
- [历史构建消耗较大] → 版本去重、范围合并、单来源互斥、队列上限和工作单元预算；返回后台状态，不占满用户 Job。
- [跨 PostgreSQL/Qdrant 无分布式事务] → 不可变候选、确定点 ID、就绪清单和数据库条件切换；故障保持旧快照。
- [相同向量在多个快照重复存储] → 首期换取简单隔离；记录容量，后续仅在实际测量必要时增加更复杂共享点结构。
- [新增源码访问面] → 仅内部提取 Job 的快照/范围授权、现有 Secret 与审计隔离、固定读取工具；源码准入与保留遵守当前安全边界。

## Migration Plan

### Runtime SDK 与初始化审计补齐（2026-11-06）

Python Runtime 固定 `claude-agent-sdk==0.2.178`，使用随包 CLI 2.1.318，不独立漂移 CLI。保留宿主注入冻结 Skill、五个文件工具、无 MCP/Bash 的提取模式。源码 `PreToolUse` 使用 `on_failure="block"`；已知校验失败返回安全拒绝及可修复错误码，意外授权异常返回固定拒绝，SDK 回调或返回值处理失败仍由 CLI 阻断，不回退为允许。

提取任务对 SDK `system/init` 仅提取有界名称列表 `tools`、`skills` 与 MCP 的名称/状态，并保存实际安装的 SDK/CLI 版本。缺失字段保持未知，过滤非法名称、超限项并标记元数据不完整；不序列化整个消息，不保存路径、认证材料、提示词、源码或候选正文。SDK 原生 Skill 发现结果与平台注入 Skill 分别观察，不把配置清单当作 SDK 实际清单。普通 Job 的既有完整审计行为不变。

部署前验证源码来源计划和按需构建保持关闭、没有活跃提取；排空 Runtime 后，仅重建和更新两个 Runtime。验证 SDK/CLI、相同代码摘要、MES 身份目录版本及摘要与当前 API 一致、只读挂载和 readiness。新发布配置由后续显式提取启用流程处理，不改写旧 Job/Publication。此次仅执行离线回归和无模型的 CLI 初始化/容器检查，真实提取验收仍保留未完成。

1. 通过现有 Migrator 扩展代码来源、知识类型和快照/构建对象，更新 schema catalog、约束、SQLite 对应测试；不假定固定 migration 编号，不删除现有 ONES 数据。
2. 部署新版合同、Skill、Runtime bridge、后台构建和管理界面；创建并显式发布受限提取 Agent/Application/服务账号及代码 KB。默认来源计划未启用，不自动扩大任何旧授权。
3. 对当前本地允许来源执行准入、冻结和基线构建；确认范围/证据/问答样本，按已配置自动激活策略发布可用本地知识。记录无法访问的依赖和未覆盖业务。
4. 配置并核验同仓库同分支的 SVN 映射和认证引用，完成本地映射核验或建立新的 SVN 起点；再启用每日计划、发布版本预构建和历史按需构建。
5. 分别完成本地回归、真实模型提取、目标 SVN 增量/历史/恢复、权限与内网运维验收。缺少部署输入的验收任务保持未完成，不阻塞本地提案或实现任务。
6. 回滚首先停用代码来源计划和新工具授权，再切回完整旧知识快照/兼容 Publication；保留来源、构建和证据记录。若旧程序不支持新合同，只保留既有 ONES 路径，不能让旧程序解释代码类型。

## Open Questions
