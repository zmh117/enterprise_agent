## Context

发布校验与运行时鉴权共用 `is_strong_bearer_token`，该函数实际只检查长度和字符格式，没有熵计算。用户要求取消 32 字符下限。当前实现已经支持执行用户和可选 Bearer，本次不改变其配置结构。

## Goals / Non-Goals

**Goals:** 允许短 Token 完成发布、渠道就绪检查与公共入口鉴权，统一前后端提示。

**Non-Goals:** 不调整凭据存储、唯一绑定、执行权限、公共 ID、投递规则及其他模块的签名密钥要求。

## Decisions

- 将公共辅助函数改名为 `is_valid_bearer_token`，接受 1–4096 字节、不含空白的可打印 ASCII 值。保留现有格式与上限检查，取消最低长度和熵要求；不引入可配置强度策略。
- 发布校验和运行时继续共用该函数，避免仅放宽保存后仍无法调用。配置了 Bearer 时继续常量时间精确比较；空凭据或解析失败不自动降级免鉴权。
- 页面仅说明凭据引用与请求头用法。回归测试覆盖短值发布、正确请求接受、错误或缺失请求头拒绝，以及非法格式与唯一绑定。

## Risks / Trade-offs

- 短 Token 的不可猜测性由配置人决定；平台不再以长度判断强度。
- 发布和运行时版本不一致会导致行为不同 → 同步更新本地 API、Webhook Worker 与管理前端。

## Migration Plan

无需数据库迁移、凭据轮换或配置改绑。已配置短 Token 的草稿可重新校验并发布；原有合法发布配置继续可用。回退旧代码会再次拒绝短 Token。
