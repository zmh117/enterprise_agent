## Context

Windows 的 Git 行尾转换可能将构建脚本变成 CRLF。现有安装器直接执行 Python shebang，并将任意非零检测结果当作无 19c，最终产生缺少客户端的成功镜像。当前规范要求仅 tool-mcp 安装匹配架构的 64-bit 19c，缺失时 Oracle 失败关闭。

## Goals / Non-Goals

**Goals:** Windows checkout 和手动复制 CRLF 脚本均可正常构建；检测执行失败不能静默跳过；保留正常无客户端和其他 Provider 行为。

**Non-Goals:** 不修改数据库、Runtime 协议或资源发布校验；不下载或提交许可客户端；不部署远端，不将本地镜像测试当作真实 Oracle 连接验收。

## Decisions

1. 双层行尾保护：为 `backend/docker/*.py` 增加 LF 属性，沿用 shell 的 LF 属性；Docker 在执行前归一化复制进来的两个 Oracle 脚本。仅添加 Git 属性不能覆盖未重新 checkout 的旧文件或手动复制文件，因此构建边界仍需要处理。
2. 安装器显式使用 `python` 执行检测器，Docker 显式使用 `bash` 执行安装器，不依赖 shebang 或可执行位。现有 Python 基础镜像已有这两个解释器，不新增环境变量或依赖。
3. 检测器先进行可执行性预检。ZIP 检测返回 0 表示命中，专用退出码 3 表示合法 ZIP 无 19c 成员；损坏或不可读 ZIP 返回 2，其他异常保留非零退出码。安装器仅跳过 3，其余失败终止构建。不能用通用退出码 1 表示无匹配，因为 Python 自身执行故障也会返回 1。
4. 保留已有 ELF、64-bit、19c 和架构检查；合法但不含 19c 的归档仍忽略，完全未提供客户端时仍允许非 Oracle 镜像构建。
5. 用临时目录中的 CRLF、无可执行位、含空格路径和异常检测器做回归；安装器检测阶段在宿主机无副作用地测试，完整安装只在隔离 Linux 容器中验证。
6. 用户已确认扩展修复 libaio 兼容。保留发行版自身 libaio 包选择；仅在使用 `libaio1t64` 且旧名称不能加载时，从该已安装包清单定位真实 `libaio.so.1t64`，在 Oracle 安装目录建立私有 `libaio.so.1` 链接。不覆盖既有文件或链接，不修改系统库目录，不引入外部旧版 deb。主客户端先通过 64 位和架构验证，兼容链接后再做真实加载验证。此方法与 Oracle python-oracledb 安装文档的 t64 兼容建议一致。
7. 检测器增加构建期可选加载检查，显式调用 `oracledb.init_oracle_client`，确认非 Thin 且实际客户端版本为 19。构建提供 Oracle 安装目录的库搜索路径并传播初始化失败；没有客户端的分支仍不加载、不连接数据库。只检查 ELF 不能证明依赖或 Thick 加载成功，所以不能替代这个检查。

## Risks / Trade-offs

- 损坏 ZIP 会由原来的静默忽略改为构建失败 → 输出明确错误，由操作者替换归档；不放宽客户端要求。
- x64 客户端不能用于 arm64 容器 → 检查仍保留，镜像测试使用匹配平台。
- Linux CRLF 模拟不等于全部 Windows 环境验收 → 明确记录验证范围，目标主机仍需重新构建或拉取含客户端的新镜像并重建容器。
- 动态库别名不能替代依赖完整性或服务端验收 → 限制为匹配 64 位架构的发行版 t64 库，不覆盖现有文件，真实 Thick 初始化必须通过；不放宽服务端技术测试。

## Migration Plan

无数据库迁移。目标环境更新代码并准备合规客户端后，仅重建 tool-mcp 镜像和容器；使用镜像分发时拉取已包含客户端的新镜像并重建容器。失败可恢复旧镜像，但旧镜像若无客户端仍不能使用 Oracle。更新后在 Web 重新执行真实 Oracle 技术测试。
