## Context

当前 `sync_binding.interval_seconds` 的默认值及约束都是 3600，Repository 和调度器另外写死 1 小时，页面运行中提示也写死 1 小时。迁移历史不可修改。

## Goals / Non-Goals

目标是统一新旧计划的 4 小时间隔，保持首次立即执行及当前任务恢复行为。此次不增加通用定时配置，不改变采集日期窗口、重试等待或检索超时。

## Decisions

- 新增 153 迁移，固定数据库间隔为 14400，保留现有计划和 run 的关联、开关、修订及断点。PostgreSQL 修改约束和默认值，SQLite 依照现有迁移机制事务重建绑定表。
- 已有运行记录且存在下次时间的计划，将原下次时间顺延 3 小时，保持原周期的计算起点；尚未执行过的首次计划保留立即触发时间。运行中计划完成时重新按完成时间加 4 小时计算。
- 调度计算与页面文案读取绑定的 `interval_seconds`；创建计划使用单一固定常量。仅改页面或仅改默认值都会遗漏已有计划，因此不采用。
- 健康判断继续使用两倍计划周期，随间隔调整为 8 小时；活动任务互斥和重试机制不变。

## Risks / Trade-offs

- 新迁移推进 schema head，旧服务镜像可能拒绝新 schema：通过主 Migrator 和匹配版本的整套服务部署升级，不能只重启旧容器。
- 同步频率降低会增加新内容入库等待时间：这是用户指定的间隔调整，仍允许显式立即同步。

## Migration Plan

按主部署流程应用 153 并更新匹配镜像；不在请求或 worker 启动中迁移。已有任务和数据保持原状态；不修改历史迁移，不回滚到与新 schema 不匹配的旧镜像。

## Open Questions

无。真实环境部署与实际四小时触发需由该环境另行验收，本次使用隔离测试验证。
