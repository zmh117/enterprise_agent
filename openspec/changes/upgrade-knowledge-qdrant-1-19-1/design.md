## Context

当前本机以可选 knowledge Compose 运行单节点 Qdrant 1.17.0，持久卷为 `enterprise_agent_knowledge-qdrant`，仅连接 internal 网络，无公开端口。现有客户端使用固定 REST Query/Points/Count API，不依赖 Qdrant SDK；现有索引预期为 5000 文档、8309 点，实际数量和摘要须现场复核。

## Goals / Non-Goals

目标：保持数据与网络边界，升级到用户指定 v1.19.1 并固定摘要，交付备份、逐级运行验证和重启证据。

非目标：数据库迁移、重新 Embedding、MCP/角色授权、外部 ONES 调用、其他业务组件升级、通用运维自动化平台。

## Decisions

1. 按官方升级合同执行 `1.17.0 → 1.17.1 → 1.18.3 → 1.19.1`，提前取得并记录全部镜像摘要。单节点也不能跳过中间次版本；不把 latest 启动在现有卷上。[官方说明](https://qdrant.tech/documentation/upgrades/)
2. 先确认无索引写入任务，短暂停止 Qdrant，对明确持久卷制作任务专属冷备副本，校验文件摘要后恢复原服务。备份只保留在本机 Docker 卷，不输出向量或业务内容。
3. 从冷备创建独立演练卷，先用原版启动证明可恢复，再在演练卷逐版本升级，逐步检查健康、精确点数、配置、全部点/向量摘要和查询。演练容器不发布端口、不读取业务凭据。
4. 演练通过后，仅以 `--no-deps` 定向重建正式 Qdrant，逐版本核验并保留原卷名。最终 Compose 固定 `v1.19.1@sha256:<已核验 digest>`，不把临时演练配置留在正式入口。
5. 版本升级可能迁移磁盘格式，因此回退须用升级前副本和原镜像，禁止把旧镜像直接挂载已升级的数据卷。备份不自动删除，演练资源只清理本次明确创建的对象。
6. 增加现有 Compose 测试中的版本/摘要及持久卷/网络边界断言；运行现有知识测试、配置校验、严格 OpenSpec 与 Markdown 链接检查，不修改已有验收历史。

## Risks / Trade-offs

- [索引正在写入] → 先检查运行任务并确认静止，停止 Qdrant 后冷备；无法确认则不迁移。
- [升级损坏或格式不兼容] → 在隔离副本演练并保留原版可恢复备份，每一级验证通过才进入下一级。
- [Qdrant 内部布局变化但业务数据应不变] → 分开使用备份文件摘要与 API 层点/向量摘要；后者用于升级前后比较。
- [影响其他服务] → 精确服务名、卷名和 internal 网络，定向启动；前后比较其他容器身份与启动时间。
- [新镜像未匹配目标平台] → 核实 Linux ARM64 和实际二进制版本，不能仅看镜像标签。

## Migration Plan

预检及镜像准备 → 一致性备份 → 原版恢复演练 → 演练逐级升级 → 正式逐级升级 → 固定版本及摘要 → 正式重启/完整性/检索验证 → 记录证据与恢复指引。任何一阶段失败均停止推进并保留已有数据，不做自动删除或重建索引。

## Open Questions

目标版本和操作范围已由用户明确批准；镜像摘要、当前索引摘要、备份对象及实际验收结果将在执行中核实并记录。

## 后续运维镜像刷新

按后续明确授权，仅构建 `knowledge-ops` 的既有 migrator target，使用缓存且不刷新基础镜像/模型。定向重启两个知识常驻服务，等待就绪后在默认 `knowledge-ops` 镜像下执行 schema 门禁、全量点身份核验和本地合成检索，不再以主栈 migrator 临时覆盖代替默认镜像验收。对比其他容器 ID/启动时间，保留 PostgreSQL、模型/向量卷及升级前冷备。
