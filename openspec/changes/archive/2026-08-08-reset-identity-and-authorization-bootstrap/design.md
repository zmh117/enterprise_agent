## Context

“角色与授权”控制中心已经引入系统角色、角色成员、管理后台能力、业务应用访问、业务能力和明确数据范围，但当前数据库仍混有旧 `app_user`、外部身份、服务账号、`permission_policy`、`platform_access_grant` 和兼容授权来源。配置中的 `business_application_authorization_mode` 仍允许 `compatibility`，因此绑定成功不等于获得业务应用权限，旧策略与新角色并存时也很难解释最终授权来源。

本变更是一次独立的破坏性运维变更，目标是把身份和授权数据恢复为可重新配置的干净状态。用户已经明确要求不迁移旧角色和成员，全部清理后新建 `platform-admin`。同时，系统现有 Webhook Trigger、业务应用 Trigger Binding 和历史 Webhook Event 对服务账号存在强引用；直接删除 `app_user` 会违反外键或迫使删除业务配置和运行历史，因此必须先改造引用模型。

约束如下：

- 保留业务应用、Agent、渠道、Connector、运行/投递记录、未绑定钉钉候选消息和审计历史。
- 当前 Agent 保持只读诊断边界，Agent 不参与重置，也不直接管理数据库或凭据。
- 用户可见页面和错误使用中文，稳定编码、ID 和 `error_code` 可保留英文。
- Client Secret、Token、模型 API Key 和初始密码不得出现在日志、命令参数、回复或规格产物中。
- 实施时必须保留现有未提交修改，完成测试、容器重建和真实运行链路验证。

## Goals / Non-Goals

**Goals:**

- 在可验证备份、双阶段确认和维护锁保护下，原子删除全部旧身份和授权事实。
- 保留业务控制面和不可变历史，并对旧服务账号引用建立明确的快照、替代与停用策略。
- 创建唯一的启用人员管理员 `platform-admin`，只赋予 Web 管理能力，不赋予业务访问能力。
- 安全生成并一次性交付初始凭据，强制首次改密。
- 关闭兼容授权并验证所有入口只使用严格应用角色授权。
- 提供失败自动回滚、重复执行保护和提交后数据库恢复手册。

**Non-Goals:**

- 不迁移、映射或自动重建任何旧人员、外部身份、旧角色、角色成员或业务授权。
- 不自动为新管理员、替代服务账号或后续绑定用户授予业务应用、工具或数据范围。
- 不删除 Agent Job、消息、投递、审计、业务应用、Agent Profile/Publication、渠道或 Connector。
- 不通过 Web 页面提供“一键清空”，也不允许 Agent 或 Channel 触发重置。
- 不扩大当前只读工具边界，不引入写数据库、Redis 或 Loki 的 Agent 能力。

## Decisions

### 1. 使用专用离线运维命令和持久化操作台账

新增专用 Python 运维入口，由 `api-server` 镜像中的应用代码执行，但要求操作者具有容器与数据库运维权限。命令分为 `report`、`prepare`、`apply`、`verify` 和 `restore-check`，不增加 Web 重置 API。

新增 `identity_authorization_reset_operation` 台账，保存操作 ID、阶段状态、数据库/迁移版本、影响摘要、备份摘要、确认到期时间、错误码和最终不变量。状态至少包括：

`DRAFT -> PREPARED -> APPLYING -> SUCCEEDED`

失败状态包括 `PREPARE_FAILED`、`APPLY_FAILED` 和 `VERIFY_FAILED`。数据库约束保证同一时间最多一个 `PREPARED/APPLYING` 操作；`SUCCEEDED` 操作不可再次应用。

选择该方案而不是复用登录后的管理 API，是因为重置会删除当前操作者和会话，Web 请求无法提供可靠的事务、维护锁和恢复边界。

### 2. 以数据库目录驱动预检，而不是维护一份盲删表清单

实现层仍会维护受审查的删除顺序，但 `report/prepare` 必须同时查询 PostgreSQL 外键目录和应用维护的逻辑引用登记表。每个指向 `app_user`、`user_external_identity`、`rbac_role` 或角色授权表的引用必须归类为：

- `DELETE`：身份/授权事实，随重置删除；
- `SNAPSHOT_AND_NULL`：历史记录先保存安全主体摘要，再解除引用；
- `REPLACE_AND_DISABLE`：仍需保留的运行配置改绑到新替代服务账号并停用；
- `NULL_AND_RECONFIGURE`：可选 owner 等引用清空并加入重配清单；
- `PRESERVE_TEXT_SNAPSHOT`：本身已经是不可变文本/ID 摘要，无外键；
- `BLOCK`：未知或没有安全规则的引用，阻止执行。

这比只按当前已知表名删除更稳健，新迁移若增加主体引用会自动让预检失败，而不是留下悬空授权。

### 3. 物理删除旧主体，同时保留历史语义

用户要求“全部删除”，因此不把旧账号改成 `disabled` 墓碑。对历史 `webhook_event.service_account_id` 等强引用新增安全主体快照字段，将外键改为可空并使用 `ON DELETE SET NULL`；快照只保存账号类型、不可逆主体摘要和当时显示标签，不保存密码、Token、外部身份完整值或消息正文。

`audit_event.actor_id`、`created_by`、`published_by` 等已经是文本快照的字段继续保留，不作为当前有效主体解析。历史页面必须明确显示“主体已删除”，不能把相同字符串的新账号当成原操作者。

替代方案“保留停用旧账号”实现简单，但不满足清除旧身份的明确要求，也会让未绑定钉钉发现和授权解释继续混入旧主体。

### 4. 为运行配置创建全新的停用服务账号

Webhook Trigger 的 `service_account_id` 非空，不能在保留 Trigger 定义的同时置空。准备阶段按仍被配置引用的旧服务账号分组制定替代计划；执行时为每组创建新 ID、随机不可预测用户名的 `service` 账号，状态为 `disabled`，不创建密码、外部身份、角色成员或直接授权，并改写引用。

所有引用替代账号的 Webhook Trigger 和 `SERVICE_ACCOUNT` Trigger Binding 必须停用；不可变 Publication 保留原快照用于历史解释，但当前部署不得继续路由到它。管理端生成中文重配清单，管理员后续需要显式启用服务账号、分配业务角色、校验并重新发布入口。

选择替代账号而不是改绑 `platform-admin`，是为了维持人员账号与非交互式入口隔离，并防止后台全权主体被运行时滥用。

### 5. 维护模式同时覆盖控制面和运行面

新增数据库持久化维护状态 `identity_authorization_reset`。API、钉钉 Inbox、Webhook Inbox、Job dispatcher、Agent Worker 和 Delivery Worker 在关键写入点读取该状态：

- 新登录、身份绑定、人员/角色/授权写入返回中文维护提示；
- Channel/Webhook 入站可以记录有界连接状态，但不得创建 Inbox 业务事实或 Agent Job；
- Worker 不再领取新 Job，Delivery Worker 不再领取新投递；
- 已执行中的任务在有界排空时间内结束，超时则准备失败。

`apply` 获取 PostgreSQL advisory lock，并校验所有写入者租约已清零后才开启数据库事务。维护状态与 advisory lock 分别解决跨进程可见性和单执行者互斥。

### 6. 备份由准备阶段创建并独立验证

`prepare` 使用 PostgreSQL custom-format 备份，保存到操作者明确指定、仓库外且权限受限的新文件。完成后计算 SHA-256，记录服务端版本、迁移 head、文件大小，并通过 `pg_restore --list` 验证目录可读。命令从已有安全环境读取连接配置，不把 DSN 密码拼入命令参数或日志。

只接受“本次 prepare 创建并登记”的备份，`apply` 会重新校验摘要和数据库影响摘要。这样可以避免操作者误用旧备份或在预检后数据变化仍继续执行。

### 7. 数据库重置使用一个事务并在提交前验证不变量

事务内按以下顺序处理：

1. 锁定台账、身份、角色、授权及相关运行配置表。
2. 写入历史主体快照并改造可空引用。
3. 创建停用替代服务账号，改写并停用依赖入口。
4. 清空 owner 等可选当前主体引用。
5. 删除角色应用能力/范围、角色应用访问、角色管理能力、成员关系、密码、会话、外部身份、直接策略、平台授权、角色和旧用户。
6. 创建新人员账号 `platform-admin`、Argon2 密码凭据、受保护系统角色和成员关系。
7. 将授权模式写为 `strict_application_role`。
8. 验证唯一人员管理员、零旧事实、零业务授权、零悬空引用、所有替代服务账号停用、所有依赖入口停用。
9. 将台账标记为 `SUCCEEDED` 并提交。

审计成功事件在同一事务中使用 `system:identity-reset:<operation-id>` 作为运维主体快照。任何 SQL、约束或不变量失败都会回滚全部数据修改。

### 8. 一次性凭据采用仓库外的受限文件交付

`apply` 要求 `--credential-output` 指向仓库外的全新绝对路径。实现使用密码学安全随机源生成初始密码，通过 `O_CREAT | O_EXCL` 以 `0600` 创建文件并 `fsync`；标准输出只显示操作 ID、文件路径和不含凭据的文件摘要。密码只在进程内存中参与 Argon2 哈希，不写数据库明文。

文件在事务开始前安全落盘，以避免数据库已提交但凭据无法交付导致锁死；若事务失败，命令立即删除该无效文件。若进程崩溃，`verify` 根据台账状态明确标记文件无效，且只有 `SUCCEEDED` 操作对应的哈希可以登录。

没有采用命令行参数或控制台打印密码，因为两者容易进入 shell history、CI 日志和终端采集；没有硬编码默认密码，因为无法安全轮换且所有部署相同。

### 9. 首次改密是认证状态而不是前端提示

为 `user_password_credential` 增加 `must_change_password` 与可选的 `initial_credential_expires_at`。初始凭据设置短期有效期。认证成功后签发受限会话，后端能力目录只允许 `auth.password.change`、`auth.logout` 和会话自检；所有其他 API 返回稳定 `initial_password_change_required` 与中文提示。

改密成功后清除强制标记、更新 Argon2 哈希并撤销所有会话，用户必须用新密码重新登录。即使凭据文件仍存在，其中的初始密码也已失效。

### 10. 严格模式切换与缓存失效属于提交后的发布步骤

数据库事务写入 `strict_application_role` 后，所有进程必须通过配置 revision 或重启读取新模式。实施不依赖进程内长期授权缓存；若存在缓存，重置 revision 必须作为缓存键并在提交后广播失效。

退出维护模式前，`verify` 必须从 API、Channel 和 Webhook 三类入口证明：

- 新平台管理员能登录并被强制改密；
- 改密后能进入管理后台；
- 新管理员无业务应用访问；
- 旧外部身份重新进入未绑定候选；
- 停用替代服务账号无法创建 Job；
- 不存在旧策略兼容来源；
- 运行和投递历史仍可查询。

### 11. 提交后不提供“快速切回兼容模式”

事务内失败自动回滚。成功后的回退必须停止写入、导出重置后审计、校验 prepare 备份摘要、完整恢复数据库、重新运行迁移并重建容器。单独把配置改回 `compatibility` 会重新激活不可解释的旧授权，因此不作为支持的回滚手段。

## Risks / Trade-offs

- [服务账号引用分布在多张表，遗漏会导致删除失败或运行时悬空] → 使用 PostgreSQL 外键目录、逻辑引用登记表和 `BLOCK` 默认策略，未知引用必须先补设计。
- [维护窗口中消息可能到达] → 入口返回明确可重试维护状态，不创建 Job；恢复后由外部重试或管理员重新发送，不暗中丢弃已接受事件。
- [凭据文件是短期明文载体] → 强制仓库外、绝对新路径、`0600`、独占创建、短期有效、首次改密和会话撤销；不允许标准输出或命令参数携带密码。
- [备份可读但仍可能无法完整恢复] → 除 `pg_restore --list` 外，在验收环境执行一次隔离恢复演练、迁移和核心查询，再允许生产式执行。
- [严格模式导致所有旧入口立即不可用] → 这是预期的安全结果；生成完整中文重配清单，并逐个重新创建身份绑定和业务角色。
- [物理删除会失去当前主体详情] → 在历史记录写入最小安全快照，保留审计语义，但不保留可继续登录或授权的主体。
- [替代服务账号数量可能较多] → 只按实际被保留配置引用的分组创建，全部初始停用且无授权，避免无界复制。

## Migration Plan

1. 完成并严格验证 `add-role-and-authorization-control-center`，确认相关数据库迁移、管理能力目录和严格授权路径已部署。
2. 增加重置台账、首次改密字段、历史主体快照和可空外键迁移；对 PostgreSQL 与测试用 SQLite 分别实现等价约束。
3. 实现依赖登记、预检报告、备份验证、维护状态、两阶段确认、原子重置、凭据文件交付和验证命令。
4. 增加后端首次改密限制和管理端中文首次改密页面；补齐 API/Runtime/Worker 对维护状态与严格模式 revision 的处理。
5. 使用脱敏测试夹具覆盖人员、外部身份、角色、多角色授权、Webhook 服务账号、业务 Trigger、历史 Event/Job/Audit 和钉钉候选消息。
6. 运行后端全量测试、Ruff、前端测试/Lint/构建、Runtime 测试/Lint/typecheck 和 OpenSpec strict validate。
7. 在隔离数据库执行两次演练：第一次故意制造未知外键验证阻断，第二次完成 prepare/apply/verify；再从备份恢复并验证摘要。
8. 重建相关容器并确认健康后，在维护窗口执行真实重置。任何输出不得包含初始密码、Token、Secret 或模型 API Key。
9. 使用本地凭据文件取得初始密码，完成首次改密；确认旧会话全部失效。
10. 真实验证 Web 登录、管理能力、无业务授权、钉钉未绑定发现、Webhook 停用拒绝、Job 创建边界、Worker/Delivery 不被越权触发及历史查询。
11. 将重配清单交给 `platform-admin`，由管理员重新绑定用户、分配角色并逐个启用业务入口。

**回滚策略：**

- `prepare/apply` 提交前失败：释放维护状态和锁，数据库事务自动回滚，清理无效凭据文件。
- `apply` 提交后验证失败：保持维护模式，不启用任何业务入口；导出本次安全审计，使用登记且摘要匹配的备份完整恢复。
- 恢复后：应用迁移、重建容器、验证原管理员登录和原授权链路，确认无残留重置进程后退出维护模式。

## Open Questions

无。重置范围、管理员账号、业务授权为空、一次性凭据交付和提交后恢复方式均已在本变更中固定。
