## Why

系统已经具备角色、成员关系、权限策略和平台数据范围等底层能力，但管理端缺少统一的“角色与授权”入口，运行时仍要求管理员理解业务应用、项目、Agent、工具和数据范围的多层原始策略，导致身份绑定成功后仍因隐含权限缺失而被拒绝。现在需要以角色为中心统一管理后台功能权限和业务访问权限，并让授权结果可以预览、解释、即时生效和安全审计。

## What Changes

- 在“用户与外部身份”下新增“角色与授权”菜单、角色列表和角色详情页面，统一管理基本信息、成员、管理后台能力、业务应用与数据范围、有效权限预览和操作记录。
- 建立后端注册的管理能力目录，以稳定的“模块 + 业务动作 + 可选资源范围”能力编码驱动前端勾选、导航和按钮展示，同时由对应后端 API 强制校验。
- 允许自定义角色同时包含管理后台能力和业务访问能力；平台管理角色与业务访问角色作为模板或用途标签，不再作为互斥角色类型。
- 将业务访问建模为“角色 → 业务应用 → 只读业务能力 → 当前明确环境/基地/车间集合”，不向普通管理员暴露原始 `project / agent / tool / priority` 策略字段。
- 角色可拥有多个成员，用户可拥有多个角色；成员关系支持可选失效时间，多个允许范围取并集，高级显式拒绝继续优先。
- 支持按角色委派成员分配权、按授权区分离编辑权限、资源级管理范围和“不能授予超出自身可授权范围的权限”约束，阻止自我提权。
- 钉钉身份绑定流程支持同时选择多个初始角色；绑定和初始角色分配必须原子完成，也允许明确选择“仅绑定身份，暂不授权”。
- 授权编辑采用分区修订和原子提交，保存后立即生效；排队任务在执行前、运行中的业务能力调用以及结果投递前重新校验当前授权。
- 提供安全的有效权限模拟和决策说明，展示允许/拒绝、来源角色、应用、能力、数据范围及高级拒绝摘要，不泄露敏感策略或凭据。
- 保护 `platform-admin` 系统角色：自动获得当前及未来全部管理后台能力、禁止修改关键权限、禁止移除最后一名启用管理员，但不自动获得业务应用或业务数据访问权。
- 业务授权只允许已注册、已启用、应用已装配且处于 Agent 只读能力上限内的能力；当前 change 不引入任何写入型工具。
- **BREAKING**：业务应用路由下的新授权主模型从管理员手工组合 `project / agent / tool` 权限，转为业务应用访问授权所蕴含的运行入口许可；旧原始策略仅作为受控兼容和高级例外，最终清理由后续独立 change 处理。
- 不在本 change 中删除旧用户、角色、成员、身份或权限数据，也不创建或输出新的 `platform-admin` 初始密码；一次性身份与授权重置由独立 change `reset-identity-and-authorization-bootstrap` 负责。

## Capabilities

### New Capabilities

- `role-authorization-model`: 定义统一自定义角色、系统角色保护、分区授权、成员有效期、角色级分配委派、直接例外和权限合并规则。
- `admin-capability-catalog`: 定义由后端注册的管理后台能力目录、动作依赖、风险等级、资源范围和前后端一致执行规则。
- `role-authorization-admin-console`: 定义“角色与授权”菜单、列表/详情、勾选配置、成员管理、钉钉绑定初始角色、权限预览和中文交互要求。
- `business-application-role-access`: 定义角色按业务应用配置只读能力与明确数据范围，以及业务应用入口对底层项目和 Agent 使用许可的封装语义。

### Modified Capabilities

- `agent-audit-permission`: 将业务应用、角色、能力和数据范围纳入统一授权决策与安全审计，并记录授权配置变更和运行时重新校验。
- `agent-job-lifecycle`: 增加 Worker 执行前的当前授权重新校验，并定义授权撤销后的非重试终止语义。
- `platform-access-control`: 将平台环境、基地和车间范围限定到当前业务应用上下文，并要求“当前全部”保存明确资源集合而非未来资源通配。
- `readonly-tool-platform`: 将角色选择的业务能力纳入工具交集，同时继续强制应用装配、Agent 工具上限、平台启用状态和只读风险边界。
- `result-delivery-routing`: 增加投递前授权重新校验，权限已撤销时不得发送可能包含业务数据的结果。

## Impact

- 后端身份与授权模块：角色模型、成员关系、权限求值器、管理能力目录、授权解释、分区 revision、审计和 typed 管理 API。
- 业务应用、Agent job、Worker、工具执行和投递链路：携带业务应用上下文并在创建、执行、工具调用和投递阶段执行一致授权。
- 平台配置：访问授权需要支持业务应用上下文和明确资源集合，同时保留服务账号与只读工具边界。
- 前端：新增 `/users/roles`、`/users/roles/:roleId`，改造当前用户详情、钉钉身份绑定流程、管理端导航和动作可见性。
- 数据库：增加加法 migration；不得在本 change 中清理或覆盖现有身份和授权数据。
- 测试与部署：需要后端权限矩阵、事务/并发、前端交互、容器重建，以及钉钉入口到执行和投递的真实授权链路验证。
