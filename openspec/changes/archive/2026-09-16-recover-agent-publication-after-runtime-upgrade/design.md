## Context

当前 Agent Publication 在管理读取、回滚和新 Job 选择时复用了执行准入级校验。`publications()` 虽然意图把旧协议标记为只读，但兼容判断只接受当前 `1.5` 和硬编码的 `1.3`；协议问题修复后，更早 Publication 又会因冻结的 MCP 工具执行策略与当前代码 Manifest 不同而使整个历史列表失败。当前数据中 r30 为 `1.5`，r29 及更早版本包含 `1.4` 和历史工具策略，与现场故障一致。

管理员恢复系统需要能够读取历史事实和当前草稿，再通过正常发布流程生成当前协议 Publication。恢复不能以放宽 Job 创建、回滚或 Runtime 加载校验为代价，也不能改写不可变历史快照或静默改变业务应用固定版本。

## Goals / Non-Goals

**Goals:**

- 任意结构合法、哈希有效、冻结工具事实一致且协议版本列表格式合法的非当前协议或历史工具策略 Publication 均可在管理面只读展示。
- 当前 Publication 已落后于平台协议时，Agent 详情明确提示并提供创建恢复草稿的可发现入口。
- 恢复草稿继续经过现有字段校验、模型连接校验、工具冻结和发布事务，生成使用当前协议的新 Publication。
- 回滚和新 Job 创建继续只接受当前可执行 Publication；已经固定 Publication 与协议的既有 Job 不被改写。

**Non-Goals:**

- 不为旧 Runtime 协议补兼容执行或自动迁移快照。
- 不原地修改 Agent Revision、Publication、工具信封或配置哈希。
- 不自动更新或重新发布业务应用。
- 不新增数据库表、后台自动恢复任务或通用迁移框架。

## Decisions

### 1. 将执行兼容判断拆为不可变事实完整性与当前平台兼容性

协议判断返回 `current` 或 `historical_read_only`，不再因一个格式合法的未知旧版本直接抛错。MCP 校验拆为“快照与冻结行一致”和“冻结策略仍匹配当前代码 Manifest”：前者失败代表事实损坏并继续报错，后者失败代表平台升级漂移并在管理面降级为只读。新执行选择路径 `_verified_publication()` 仍显式要求综合结果为当前兼容；已经创建的 Job 继续使用其固定的 Publication、协议和 Runtime 规则。

选择该方案是因为“历史版本是否可展示”和“版本是否可执行”是两个不同问题。备选方案是在白名单中继续补 `1.4`，但下一次协议升级会重复故障，不能满足升级后的自助恢复目标。

空值、非数组、重复项或非版本字符串仍视为发布事实无效并失败关闭；本变更不掩盖损坏数据。

### 2. 管理详情与历史列表使用同一兼容状态

Agent 详情中的 `current_publication` 和发布历史项都返回 `runtime_protocol_compatibility`。前端据此展示“历史协议 · 只读”，并把所有非当前协议 Publication 的回滚操作禁用。

API 返回 `runtime_protocol_compatibility`、综合 `execution_compatibility` 和有界 `incompatibility_reasons`。不新增单独的迁移状态表，因为状态可由不可变快照、冻结工具行和当前平台常量确定性计算，避免形成第二事实源。

### 3. 复用现有保存、校验、发布流程创建恢复版本

当当前 Publication 为历史协议且最新 Revision 状态为 `published` 时，原“保存草稿”动作显示为“创建当前 Runtime 恢复草稿”。提交内容仍是页面当前可编辑配置；Repository 按正常乐观并发规则创建下一 Revision。管理员随后显式校验并发布。

不新增“一键自动发布”端点，因为它会绕过管理员检查和现有三阶段门禁，也会扩大回滚与审计语义。恢复只是一个更明确的正常发布入口。

### 4. 保持业务应用固定版本边界

新 Agent Publication 只更新 Agent Definition 的当前指针。已激活业务应用继续固定其 Application Publication 中选择的 Agent Publication，管理员必须进入应用详情显式更新并重新发布。

## Risks / Trade-offs

- [历史协议版本格式过宽导致损坏值被当作历史] → 仅接受非空、去重、全部符合数字点分版本格式的字符串数组；其他值继续报完整性错误。
- [管理员误以为新 Agent 发布会立即恢复所有应用] → 保留并强化页面现有提示，明确应用不会自动切换。
- [历史工具策略被误当成事实损坏] → 分离冻结行一致性与当前 Manifest 策略比较；只对后者降级，前者继续严格失败。
- [恢复草稿与页面旧 revision 并发冲突] → 继续使用 `expected_revision`，冲突时要求刷新，不覆盖其他管理员变更。

## Migration Plan

1. 先部署后端兼容投影与回归测试，使历史列表恢复可读。
2. 部署前端状态和恢复文案。
3. 管理员刷新 Agent 详情，必要时创建恢复草稿、校验并发布。
4. 若业务应用需要使用新 Agent Publication，进入对应应用显式更新并重新发布。

回滚代码不会修改任何既有数据；若回滚部署，已生成的新 Publication 仍是合法当前协议事实。
