## Context

当前`text-v2`允许有效UTF-8、无NUL且单文件不超过15MiB的LOG只读进入任务工作区。Job最多物化40个输入，Job Sandbox总容量224MiB；模型只能通过受限`Read`、`Grep`和`Glob`自行探索原文。约20个、合计约200MiB的日志虽然可能落在现有文件数与容量边界内，但模型反复搜索会消耗大量Tool轮次和墙钟时间，并且无法给出“实际扫描了多少字节和行”的确定证据。

日志来自多个项目组，格式、时间戳、级别、堆栈和业务字段不稳定；现场排障也不以提取用户行为为固定目标。当前Runtime已经有基于冻结File MCP能力派生本地`select_sandbox_output`工具、统一Sandbox预算、Tool Call预算、墙钟取消和安全Tool事件投影，可以复用这些边界增加一个业务只读、本地有临时文件副作用的扫描工具，而不引入新的File Service数据权限。

本设计只覆盖单个Job现有硬上限内的日志集。超过40个输入、224MiB总Sandbox容量、15MiB单文件或3600秒Job墙钟上限的任务，需要后续持久化分析运行与分片编排，不在本变更内。

## Goals / Non-Goals

**Goals:**

- 让程序在一次Tool调用中以有界内存遍历选中LOG的全部字节，并返回可验证覆盖统计。
- 在日志格式未知时仍通过固定通用标志、有界字面关键词和保守多行上下文生成诊断证据，而不声称已经理解未知语义。
- 把有界原文证据写入当前Job的临时`work/`证据包，让模型按文件和行范围读取，避免把大段正文塞入MCP JSON或持久化Tool事件。
- 复用Job冻结文件身份、已物化输入、Sandbox配额、Tool预算、墙钟取消和现有Tool合同观测；不授予对象存储、网络或沙盒外权限。
- 对约20个、合计约200MiB的合成异构UTF-8 LOG建立回归和部署验证证据。

**Non-Goals:**

- 不定义用户行为事件schema，不要求项目组统一日志格式，也不建立项目级解析Profile或配置DSL。
- 不支持模型提供正则、代码、Shell、JSONPath、输出路径或其它可执行表达式。
- 不改变UTF-8、15MiB单文件、40输入、64文件、224MiB容量、Tool Call或墙钟预算上限。
- 不增加非UTF-8猜测/转换、Docling日志处理、向量数据库、全文索引、跨Job缓存、持久化分片、断点续跑或后台分析状态机。
- 不自动提交证据包或最终报告，不改变既有两阶段File Commit与Delivery边界。

## Decisions

### 1. 采用Runtime派生本地Tool，而不是File Service远端Tool或通用执行器

模型可见名称固定为`mcp__file_service__scan_log_evidence`，本地Server Tool名固定为`scan_log_evidence`。仅当当前Job绑定有效Sandbox且冻结的File MCP工具包含`file_prepare_materialization`时，Runtime才注册它；Tool合同把它记录为`runtime_derived`，依赖项为`file_prepare_materialization`，并包含固定schema hash和Runtime build identity。

调用只接受已经成功物化的`inputs/*.log`安全相对路径。Runtime以Sandbox已提交输入身份和实际文件状态重新校验普通文件、非符号链接、格式、唯一性和数量；它不接收File/Version ID、对象键、URL或凭据，也不调用File Service或网络。该调用计入当前attempt的`max_tool_calls`，并服从同一个剩余墙钟与取消信号。

选择Runtime派生Tool是因为日志字节已经在当前Job Sandbox，本地单次顺序读取可避免再次传输和新的数据权限。把它做成File Service远端Tool会让大段正文跨MCP边界；开放Shell/Python则破坏当前固定只读工具面。

### 2. 使用固定小Schema和通用扫描规则，不引入日志格式Profile

输入schema固定为：

- `relative_paths`：必填、1至40个唯一POSIX相对路径，只允许`inputs/*.log`。
- `literal_terms`：可选、最多32个UTF-8字面词，每项1至128字符且总编码字节有固定上限；按不区分ASCII大小写的字面包含匹配，不解释为正则。
- `context_lines`：可选、0至20，使用代码固定默认值。
- `max_evidence_items`：可选、1至500，使用代码固定默认值。

调用方不能提供解析Profile、时间格式、时区、级别映射、字段映射、任意正则、代码、输出路径或证据包容量。扫描器版本随Runtime代码发布，并在结果中返回固定`scanner_version`。

扫描器逐文件单次顺序读取并计算精确`size_bytes`、`scanned_bytes`、逻辑行数和SHA-256。候选证据只来自代码固定的常见故障/级别标志、调用方字面词以及围绕命中行的保守上下文；缩进续行、常见stack/traceback continuation可以并入同一证据块，但必须标记为启发式。无法唯一判断时间、级别、用户或业务动作时返回`UNKNOWN`或不产生该字段，不猜测。

固定解析Profile适合稳定协议日志，但与当前多个项目组的异构输入冲突；让模型传入正则或脚本虽然灵活，却会产生拒绝服务、逃逸和不可复现风险，因此均不采用。

### 3. 全量扫描事实与有界证据选择严格分离

“扫描完成”只表示每个选中输入的全部字节被顺序读取并通过一致性检查。证据选择按固定优先级和确定顺序保留字面词命中、致命/错误/异常、警告及其上下文；同一原文块以精确内容hash去重，不使用删除时间、ID或数字的激进模板归一化。

扫描器生成一个UTF-8 Markdown证据包，固定写入`work/log-evidence-<request_digest>.md`，最大4MiB。每条证据包含物化相对路径、起止行、起止字节、命中种类、精确片段hash和原文片段；原文必须使用确定性转义或不会被原文闭合的代码块封装，并明确标为不可信数据，日志中的指令、Tool名、Markdown或HTML不得提升为Runtime指令。包头包含输入列表的身份摘要、逐文件/总体扫描统计、候选数、保留数、`evidence_limit_reached`和所有未知/限制。Tool JSON只返回证据包相对路径、大小、SHA-256、覆盖计数、候选/保留计数和限制标志，不返回证据正文。

达到条目或4MiB证据上限时，扫描仍继续到全部输入EOF并返回成功，但必须设置`evidence_limit_reached=true`和被省略候选计数。这是显式有界选择，不是静默截断输入；Runtime提示必须禁止模型把它表述为完整语义审查。

直接把所有命中放入MCP JSON会撞上Tool响应和事件持久化边界；让模型逐次`Grep`/`Read`无法证明覆盖且正是现有超时模式，因此采用临时证据包。

### 4. 证据包复用统一Sandbox预算并保持同请求幂等

`request_digest`由scanner版本、按请求顺序的已物化输入身份/内容hash和规范化参数计算。同一Sandbox内重复相同请求时，如果现有证据包大小与hash匹配则直接复用，不再次扫描或占用第二个文件名额；参数或输入不同产生不同digest。

扫描开始前，Runtime必须为一个`work/`文件和最多4MiB容量执行原子预留，并保证当前输入、证据包、预期最终报告及现有文件仍不突破64文件/224MiB共享边界。写入过程使用不对模型可见的受控未完成状态；只有扫描、flush、UTF-8和hash校验全部成功后才发布证据包路径。取消、墙钟耗尽、超长单行导致内部有界缓冲无法处理、读取内容漂移或写入失败时，删除未完成内容并释放预留。

证据包只是当前Job的临时工作文件，不可直接作为LOG修改或原文件表示，不自动调用`select_sandbox_output`或`file_create_commit_intent`。用户要求报告时，Agent另行生成`outputs/*.md`并遵循既有显式提交和交付流程。

### 5. 原文只留在授权数据面，持久化事件只记录安全元数据

证据包位于当前Job隔离Sandbox，继承原LOG的当前Job授权，可以保留现场排障所需的用户名、业务字段、请求信息、堆栈和原文片段；本变更不新增业务字段脱敏或用户行为删除。

扫描Tool的Runtime事件、`agent_tool_call`、错误、审计和队列消息只能持久化：scanner版本、输入/扫描字节与行计数、证据计数、包大小/hash、限制标志、耗时和稳定错误码。它们不得包含字面关键词原值、输入正文、原文片段、完整证据包、模型Prompt、认证Header、Token、Cookie、密码、模型Key、对象键或MinIO位置。既有最终报告提交与交付属于用户授权的业务结果，仍遵守当前文件和渠道授权；运维可观测性不得复制该正文。

这一区分允许排障Agent看到必要原始证据，同时不让原始日志通过Tool事件、审计和消息队列产生额外持久副本。

### 6. 最终报告必须声明事实、启发式与推断层级

Runtime系统提示要求Agent优先调用一次扫描器，再按证据包的文件/行定位进行少量`Read`核验。报告至少包含：选中输入与扫描覆盖、精确计数事实、关键原文证据定位、诊断推断、未知项和证据选择限制。用户行为不是必填章节；只有日志证据支持且与排障相关时才记录。

如果任一选中输入未扫描完成，Tool调用必须失败且不得返回`coverage_complete=true`。如果扫描完整但证据达到上限，报告可以给出诊断但必须明确证据为有界选择，不能声称语义覆盖全部日志。

只提高`timeout_seconds`仍会保留反复搜索模式；对全部日志做LLM Map/Reduce会增加大量模型调用、成本和持久编排。本变更先用确定性单次扫描解决当前200MiB量级，只有真实负载持续超过现有Job边界时再提出独立可续跑分析change。

## Risks / Trade-offs

- [通用标志可能漏掉项目自定义错误语义] → 允许模型提供有界字面词，完整报告必须声明未知格式；后续只在有真实稳定需求时增加代码版本化规则。
- [4MiB证据包不能保存所有候选] → 扫描继续覆盖全部字节，返回候选/保留/省略计数和限制标志，Agent按行定位补充读取。
- [约200MiB输入给224MiB Sandbox留下空间有限] → 证据包固定上限4MiB并在扫描前原子预留；容量不足完整拒绝，不临时扩大沙盒或覆盖输出分区。
- [超长单行或巨大堆栈可能扩大内存] → 行和证据块使用代码固定缓冲上限；越界返回稳定错误，不截断后声称成功。
- [新增Runtime派生Tool会改变File Job可见工具集] → 仅依赖已冻结的只读物化权限，不增加文件身份或业务副作用；Tool合同记录派生来源、schema hash和Runtime build identity并做跨进程校验。
- [用户要求保留原文可能把敏感凭据带入最终报告] → 本变更不扩大现有原LOG读取权；运维事件始终不复制正文，最终报告仍由Agent按排障必要性选择并走当前文件/渠道授权。

## Migration Plan

1. 先部署能够验证新Runtime派生Tool合同和安全事件摘要的控制面、Agent Worker及调试投影；协议字段和数据库结构不变。
2. 再部署包含扫描器、Sandbox预留和提示更新的Python Runtime；旧Runtime不暴露该工具，回滚时不会留下持久扫描状态。
3. 使用合成异构日志验证安全路径、未知格式、取消清理和约20×10MiB批次；若目标业务应用仍需要更长模型写报告时间，通过新的Agent Revision与Business Application Revision同时设置不超过3600秒的超时并重新发布，既有Job快照不改写。
4. 观察扫描耗时、扫描字节、证据上限命中率、Tool调用数和Job终态；不得仅以容器healthy代替真实批次验证。
5. 回滚时先停止领取新的日志扫描Job，再回滚Python Runtime和控制面；证据包随Job Sandbox清理，无数据库或对象存储迁移。

## Open Questions

无。超过现有Job文件数、容量或墙钟边界的持久化分片与断点续跑明确留给后续独立change。
