## Context

现有唯一解析键为资源类型、环境、基地、车间及 placement；资源名称不参与定位。placement 存在资源身份上，枚举仅 cloud/edge，Web 表单没有输入入口。用户已确认资源角色只用于选择实例而非授权。

## Goals / Non-Goals

**Goals:** 同目标多数据库明确区分；可创建角色和复用历史值；编辑发布前不影响运行；旧云边数据兼容。

**Non-Goals:** 不新增授权层级，不开放 Loki 角色，不自动选择数据库或根据名称迁移，不自动变更现场配置或部署。

## Decisions

1. 保留 API / MCP 字段名 `placement` 并扩展为有界资源角色字符串；页面使用“资源角色”。允许中文、字母数字和 `_ . : -`，去首尾空白，不接受控制字符及内部空白，长度至多 64；空值为未指定。值精确匹配，旧 cloud/edge 原值保留，不自动互译“云”“cloud”。一个字段避免与新 resource_role 并存造成双重选择。
2. Draft 和 Revision 新增 placement；迁移从旧身份字段复制原值，空值仍空，不重写旧发布哈希。身份旧字段仅为历史兼容留存，新调用只读取最新 Published Revision 的 placement。新草稿、修改、从历史版本建草稿均计算包含角色的新哈希。升级前草稿须保存后重新验证，不能复用未覆盖角色的旧验证。
3. 角色不是环境/基地/车间的下级授权目录。历史候选从已保存 Draft / Revision 的非空角色去重获取，跨资源复用，不额外建立角色管理后台；管理端读取已加载资源元数据形成选项，不读取凭据。新角色保存时自然记录，不预置 cloud/edge。
4. 目录继续返回 placement 和精确解析状态；工具 Schema 放开固定枚举并说明多候选先询问用户。空值不表示默认库，多候选仍失败；同角色重复资源仍 AMBIGUOUS。授权仍先校验业务目标，不添加角色 Grant。
5. 已有资源从发布版本创建草稿后可修改角色，保存令旧验证失效，发布后切换到新版本角色；不修改历史版本或其他资源。角色修改走现有乐观并发与审计。
6. Loki 原有拒绝 placement 的规则不变，页面不显示该输入。数据库及 Redis 采用相同资源选择语义。

## Risks / Trade-offs

- 既有用户未填角色时仍可能多命中 → 页面和 Agent 明确提示选择，不引入默认候选。
- 工具 Schema 更新影响已发布 Envelope → 保持旧 Job 快照不变，升级后按现有规则重新发布 Agent / 应用，新 Job 使用新契约。
- 迁移涉及既有数据库 → 新增增量迁移，不修改旧 SQL；旧发布的角色语义保持，旧草稿要求重新保存验证。不在本次自动升级运行数据库。
- 工作区另有知识导入迁移 → 使用下一可用迁移编号并保留既有修改，验证时明确依赖当前工作区 schema。

## Migration Plan

准备增量迁移和代码后，在隔离测试库验证升级；部署窗口统一升级 API/tool-mcp/相关 Worker 与管理端，运行 migrator，再重新发布受工具契约影响的 Agent/应用。现场对两条 Oracle 显式补角色、技术验证和发布，新 Job 验收。没有真实数据库验收不宣称现场可用。
