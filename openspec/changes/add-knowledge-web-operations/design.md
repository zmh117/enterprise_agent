## Context

用户确认同机独立 Compose，三个 ONES 类型库由一条 sync_binding 分流。现有 sync_run/sync_candidate 已保存增量断点，管理 Web 尚无运维 API。现有 YAML 是根项目扩展，新入口不能直接改变旧项目名称并创建空卷。

## Goals / Non-Goals

目标：网页和 knowledge.sh 共用持久化任务；服务停止后控制入口仍可用；显示真实阶段、计数、心跳、错误和安全日志；首次立即同步并可恢复补采。

不引入分布式任务平台、任意命令执行、多机集群、外部内容库写入或自动发布。真实 ONES 与当前生产服务不作为测试对象。

## Decisions

1. 主项目 opt-in 扩展运行常驻 knowledge-ops-controller；只有该服务可访问 Docker socket、可信只读部署源码和配置。独立 knowledge/deployment.compose.yml 不定义主 PostgreSQL/migrator，使用显式外部网络及命名数据卷。控制器首次安装及数据库迁移由原部署负责。
2. knowledge schema 增加 operation、event、runtime 状态，网页管理权限及 CSRF 校验后提交有限枚举操作；CLI 在已安装控制器内提交同一记录。任务带幂等键、不可变参数、执行者、错误码、心跳和关联 run_id。日志仅允许结构化安全字段，绝不保存子进程原始输出。
3. 构建采用任务版本标签，构建完成不切换运行服务。启动应用最后成功构建，先核验 schema 和数据卷，再准备缓存模型、启动并检查就绪。停止先通知同步进程保存断点，再停检索/推理/向量服务；控制器及主项目保持运行。
4. 控制器执行过程持有本地持久化排他锁；重启核对 up/stop 实际状态，无法证明完成的任务报告中断，由显式重试恢复，禁止盲目宣称成功。后台同步保持来源互斥和确定 run_id，在进程重启后续跑。
5. 新常驻同步调度器串行执行已有 CLI once 子进程，不复制采集/分块逻辑。按计划调度，补采排队且沿用固定日期；先续跑当前 run，不让新范围覆盖它。每计划自动调度开关独立于已有采集安全开关，暂停自动调度不打断当前任务。瞬态错误有限重试，耗尽后显示需重试，避免一库故障永久阻塞其他来源。
6. 管理 Web 轮询服务快照、计划和任务，按需分页读取事件。分库统计仅聚合当前 run 的候选，不扫描历史库；长任务未知总量时显示阶段与数量，不伪造百分比。资源发布状态保持原语义。
7. 已有采集配置可直接接入，也提供受验证的配置入口。来源范围变更继续遵守现有不可变规则；外部数据库资源不自动纳入受管写入。

## Risks / Trade-offs

- Docker socket 等同高权限控制 → 单独执行器、固定 Compose/服务/命令、无任意路径和 shell 输入；这不是容器级权限隔离的替代。
- 原始构建或容器输出可能含敏感内容 → 不持久化原始文本，只记录允许的阶段、计数和错误码。
- 旧卷、网络或 Secret 路径未知 → 模板要求运维首次明确绑定；不自动读取真实配置或搬迁数据。
- 构建或启停时执行器失联 → 状态未知/中断与实际服务快照分开，不把心跳过期解释为任务失败或成功。

## Migration Plan

统一迁移增加表/字段；构建主程序及控制器；显式配置外部网络、数据卷、固定源码和 Secret 文件；先停止旧 daemon，接管原卷后启用新入口。回退前排空新任务并停止新同步进程，使用保留的旧部署入口；不删除卷或已生效增量内容。

## Open Questions

无设计阻塞；现场网络名、卷名和 Secret 文件位置属于安装配置，不读取真实值用于开发。
