## Context

当前 Trigger Publication 直接保存 Agent 与投递，Dispatcher 将其传入 ChannelIngressService 再与活动应用比较。应用前端暴露了未接通的私聊投递，并要求人工填写服务账号和路由键。现有业务授权、机器账号、机器人逐目标投递和应用唯一入口可复用。

## Goals / Non-Goals

**目标：** 接入配置与应用执行配置分离，Webhook 只选择业务角色；应用统一选择 Agent 和投递，支持同企业钉钉人员多选及空名单不发送。通用 JSON 固定 id/message，Grafana 使用平台内置映射。

**范围之外：** 不新增通用工作流引擎、动态外部回调 URL、角色绕过、跨企业身份猜测或真实凭据演示；不发送未被用户明确要求的真实消息。

## Decisions

1. Webhook 使用简化的版本化配置，只保存适配器、Bearer 凭据引用和业务角色 ID。保留平台固定输入上限、去重与速率控制。旧的自定义映射、Agent 和投递配置不再接受新写入。
2. 继续复用自动创建的专用 service 身份及当前角色求值；发布时经现有角色委派授权同步机器身份的业务角色。前端只显示角色，不暴露人员维护入口。角色必须启用且不含管理后台权限；接收人不参与执行授权，也不提供个人 ONES/钉钉凭据。
3. Agent Publication 固定允许的入口 Connector。应用触发器候选由已选择的 Agent Publication 与当前启用 Webhook 交集产生；服务端重验。Webhook 选择自动填充来源、规范化路由和机器身份。
4. 保持单个 Webhook 路由只归一个活动应用。认证和固定报文解析后，受理时固定应用 Publication 和 Agent Publication；Dispatcher 仍需通过当前路由和权限复核，版本不一致则失败，不替换到新应用配置。
5. 应用 dingtalk_private 投递保存机器人 Connector 和内部人员 ID 数组（最多 20 人）。发布时校验并固定同企业外部身份，发布与发送前复核启停和绑定归属。复用逐收件人 Delivery Outbox，不新建另一套发送机制。空名单或未配置投递使用 none，Job 正常完成并保留结果。
6. 高级区保留 HTTP 回调，选择受管出站 Connector 和安全目标引用，不接受任意 URL、凭据或外部报文覆盖。删除 webhook_result 投递类型。
7. 先完成迁移及接口，再调整三个前端页面和回归测试；保存草稿不切换发布或发送真实消息。

## Risks / Trade-offs

- 发布时角色委派可能失败 → 复用现有授权服务，在同一事务内拒绝发布，不产生部分角色变更。
- 人员解绑、跨企业或停用 → 候选过滤，服务端重新校验，冻结身份与当前归属不一致时停止该目标投递，不改投其他人。
- 队列期间发布变化 → 固定事件关联，冲突显式失败；不把新发布配置套入旧事件。
- 历史配置包含已删除字段 → 旧 Webhook 停用并提示重新配置发布，历史审计/Job 保留；不为旧自定义映射增加兼容执行分支。

## Migration Plan

追加迁移解除 Trigger 对 Agent Publication 的强制引用，并为不产生 Job 的拒绝事件允许空 Agent 引用。旧 Webhook 失效后需按简化配置重新发布，既有应用需要更新为应用投递配置。先迁移再统一更新 API、Webhook/渠道/Agent/投递 Worker 与管理页面，部署前记录受影响对象数量，不读取凭据或原消息。

## Open Questions

用户已确认固定通用 JSON 加 Grafana、空收件人不发送、保留高级 HTTP 回调。角色选择复用现有多角色合并语义，其工具和范围仍必须属于目标应用授权。
