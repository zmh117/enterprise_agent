## 背景

当前 Webhook v2 配置包含 role_ids，并创建独立 service 用户；真实入口已进入 Job，但知识门禁拒绝非 human。用户已明确选择只绑定执行用户，并授权把“测试webhook”绑定 Administrator（admin）。

## 目标与范围

Webhook 配置页提供执行用户下拉框，只显示启用人员。直接复用该用户的业务权限、外部身份和个人凭据解析链路。接收人仍在应用投递内设置。避免引入新的角色主体、任意代理权限或个人凭据复制。

## 决策

1. Webhook schema v3 的配置由 adapter、authentication、execution_user_id 组成；保存严格拒绝 role_ids，发布与回退验证用户存在、启用且为 human。目录仅投影 ID、用户名、显示名。管理已有 Webhook 的权限是设置执行身份的权限；页面明确说明身份用途。
2. 定义增加可空 execution_user_id，作为当前发布的只读索引；草稿允许尚未选择人员，但保存配置和发布要求明确人员。创建/保存/发布不修改人员及其角色。发布与回退在事务内同步定义索引，接收验证其与不可变快照一致。
3. 事件将 execution_user_id 固定为接收时发布中的用户。分发仍核对该用户状态、发布完整性与应用授权，并以同一用户创建 Job。外部 payload 的用户、角色或身份字段不能覆盖控制事实。
4. 应用 Webhook 使用 BOUND_USER 与 execution_user_id，服务端从所选 Webhook 当前发布解析；新应用发布 schema v8 保留每触发器投递语义。执行前核对应用冻结用户与事件用户一致，重新绑定后需重新保存、发布并激活应用。旧钉钉发布仍有效；旧 Webhook 发布必须重新配置，不能自动猜执行用户。
5. 知识库与 MCP 保持 RUNNING Job、human、冻结授权与当前权限交集合同；个人身份继续从 Job 用户解析。工具自身的入口限制保持有效，钉钉个人 MCP 仍要求钉钉来源 Connector，Webhook 不自动选择机器人代替来源。写入仍要求本人确认，不把收件人视为确认者。

## 迁移与部署

迁移增加定义的新用户索引并删除旧服务账号字段；事件的历史执行主体列改名，保留审计数据；应用 Trigger 列改名并移除旧服务策略的数据库枚举约束。旧 Webhook 全部停用并撤销发布，待明确选择用户后重新发布；不删除无关人员、角色或聊天历史。无需兼容执行旧 Webhook。

先完成回归再更新 API、入口、执行与 MCP 授权消费者。核对真实配置后为 test-webhook 选择 admin，并更新引用该入口的 assist03 草稿/发布与活动路由。只发送新的合成测试事件；失败事件不重放。

## 风险与处理

- 用户被停用或权限撤销：接收/分发/工具调用失败关闭，不切换发布者或收件人。
- 重新绑定影响待分发事件：事件保存原用户，不能使用定义的新用户替换。
- 组件版本混用：核对每个消费者的 schema 和相关回归；就绪不等于真实聊天验收。
- 历史 service 用户：仅保留历史审计引用；新 Webhook 不再创建或使用，不扩大其权限。

## 待定事项

无。执行用户已由用户选择为 Administrator（admin）；没有其他委托或自动确认需求。
